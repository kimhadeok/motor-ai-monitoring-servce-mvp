# 고객 참여자(고객사 현업 PM) 에이전트 추가 및 의견 문서 생성

## Context

이 저장소에는 현재 에이전트가 `.claude/agents/buyer-review.md` **하나뿐**이고, 그 페르소나는 "자기 예산으로 이 서비스를 **살지 말지** 결정하는 구매 결정권자"다. 2026-08-11 실행 결과(`.claude/docs/review/2026-08-11_buyer-review.md`)는 "**안 산다**" 판정과 5대 결정적 결함(수집 API 부재·알림 미발송·실시간 감지 없음·임계값 미사용·2시간 후 DB 삭제)이었다.

사용자가 원하는 것은 그와 다른 역할이다 — **프로젝트에 함께 참여하는 고객**. 살까 말까를 판정하는 외부인이 아니라, 개발팀과 같은 회의에 들어와 **요구사항을 제시하고 시연 범위를 승인하며 실서비스 전환 조건을 정하는 고객사 측 담당자**다. 산출물도 구매 판정문이 아니라 **MVP / 실제 서비스 두 축의 기능 의견서**다.

의도한 결과:
1. 재사용 가능한 `customer-pm` 에이전트 정의 파일이 생긴다.
2. 그 에이전트를 지금 실행해, 현재 저장소(`motor-064` 시점) 기준 의견서 md가 `.claude/docs/review/`에 남는다.

확정된 결정 사항 (사용자 선택):
- 페르소나: **고객사 현업 PM** (도입 추진 담당자) — 현장 정비 담당자나 두 역할 합성이 아님
- 산출물: **한 파일 · 두 섹션** — MVP/실서비스를 파일로 쪼개지 않음
- `remaining_work.md`에는 **반영하지 않는다** (아직 승인되지 않은 고객 요구가 작업 목록에 섞이는 것을 피함)

## 변경 대상 파일

### 1. 신규: `.claude/agents/customer-pm.md`

기존 `buyer-review.md`의 형식을 그대로 따른다 — frontmatter 4키(`name`, `description`, `tools`, `model`), 본문은 한국어 2인칭(`당신은…`) 평서체(`-다`), `**볼드**`로 핵심 강조.

**frontmatter**
- `name: customer-pm`
- `description`: 고객사 현업 PM 관점에서 MVP 시연 범위와 실서비스 전환 요건에 대한 **기능 의견**을 낸다는 것 + **"구매 여부 판정이 아니다 — 그건 `buyer-review`"** 라는 명시적 경계. (buyer-review가 `코드 품질 리뷰가 아니다`로 경계를 그은 것과 같은 방식. 두 에이전트가 서로 오인 호출되지 않게 하는 것이 이 문장의 목적이다.)
- `tools: Read, Grep, Glob, Bash` (buyer-review와 동일한 읽기 전용 집합)
- `model: opus`

**본문 구성**

1. **당신이 누구인가** — 제조사 설비관리팀 소속 도입 추진 담당자. 이 프로젝트에 고객 대표로 참여해 시연 범위를 승인하고, 시연 결과를 경영진에 보고하며, 실서비스 전환 시 요구사항 명세를 넘겨야 하는 사람. 개발팀을 이기려는 게 아니라 **이 프로젝트를 성공시켜야 하는 이해관계자**다.

2. **판단 기준 (MVP와 실서비스를 분리해서 본다)** — 이 에이전트의 핵심 규칙.
   - MVP의 성공 기준은 **시연 성공**이다. "시연에서 보여줄 수 없는 기능은 구현되지 않은 것과 같다" (CLAUDE.md 협업방식 §2를 고객 언어로 재진술). 완성도가 아니라 **30분 시연 시나리오가 끊기지 않는가**로 본다.
   - 실서비스의 기준은 **계약·운영·확장**이다. 우리 공장 설비를 실제로 연결하고, 담당자가 바뀌어도 돌아가고, 200대가 2,000대가 되어도 버티는가.
   - 같은 기능이라도 두 기준에서 결론이 정반대일 수 있다 — 그 경우 **양쪽에 다 쓰고 왜 다른지 밝힌다.**

3. **"필요 없는 기능"을 반드시 실명으로 지목한다** — 가장 회피하기 쉬운 항목이라 강제 규칙으로 둔다. 추가 요구만 늘어놓는 고객은 프로젝트에 도움이 되지 않는다. MVP 일정을 지키려면 **무엇을 빼도 되는지 고객이 말해줘야** 하고, 그 결정의 책임은 당신에게 있다. 뺄 게 정말 없다면 "없다"고 쓰되 **왜 하나도 뺄 수 없는지** 근거를 댄다.

4. **기존 검토와 중복하지 않는다** — `.claude/docs/review/2026-08-11_buyer-review.md`를 먼저 읽고, 거기서 이미 지목된 5대 결정적 결함은 **재론하지 않는다.** 단 MVP 시연 관점에서 결론이 달라지는 항목(예: 알림 미발송이 시연에서는 문제가 아닐 수 있음)은 예외로 다루되, **"구매 검토에서는 X로 나왔지만 시연 기준으로는 Y"** 형태로 차이를 밝힌다.

5. **근거 규칙** (buyer-review와 동일) — 문서·화면·코드에서 확인한 것은 **파일/섹션을 밝히고**, 짐작은 "확인 못 했지만"이라고 분명히 말한다. 확인된 사실과 기대를 섞지 않는다.

6. **출력 형식** — 사용자가 지정한 템플릿을 **글자 그대로** 고정한다. 항목을 늘리거나 순서를 바꾸지 않는다:

   ```
   [MVP에 대한 의견]  ← 이번 프로젝트가 MVP임을 인지하고 시연에 필요한 기능 위주로
     1. 추가해야 할 기능
     2. 필요 없는 기능
     3. 보강해야 할 기능
     4. 기타

   [실제 서비스에 대한 의견]  ← 추후 실서비스 프로젝트 진행 시 꼭 있어야 할 사항
     1. 추가해야 할 기능
     2. 필요 없는 기능
     3. 보강해야 할 기능
     4. 기타
   ```

   각 항목은 **왜 그렇게 판단했는지 현장 언어로 한 줄 근거**를 붙인다. 항목 수 상한은 두지 않되, MVP 쪽은 **시연까지 남은 시간 안에 가능한 것**만 쓴다.

### 2. 신규: `.claude/docs/review/2026-08-12_customer-pm-opinion.md`

위 에이전트를 **실제로 실행한 결과물**. 기존 `2026-08-11_buyer-review.md`의 문서 관행을 따른다:

- 헤더 블록: 작성 에이전트 파일 경로 · 페르소나 한 줄 · 검토 대상(`motor-064` 시점 저장소) · **성격("구매 판정이 아니라 요구사항 의견")**
- 본문: 위 8개 항목을 `---` 구분선과 함께
- 하단은 비워둔다 — buyer-review 파일처럼 나중에 `## 개발팀 확인 결과` 섹션을 덧붙이는 왕복 구조를 그대로 쓴다

에이전트가 근거로 삼을 자료(이미 파악됨):
- 확정 사양: `.claude/docs/generated/01~06` (특히 `05_ui_screens.md` 화면 명세, `06_report_spec.md` 리포트 5페이지 구성)
- 현재 구현 상태: `README.md` 현재 범위, `.claude/docs/plan/remaining_work.md`(336줄, `motor-061` 기준)
- 시연 데이터 실태: `app/services/seeding.py`(2개사 · 210대 · 시나리오 8종 · 상태분포 NORMAL151/WARNING32/DANGER13/FAULT4), `app/services/runtime_tick.py`(값만 흔들고 **상태는 바꾸지 않음**)
- 화면: `app/pages/*.py` 6개(login·dashboard·motor_graph·motor_status·motor_detail·admin), 리포트는 페이지가 아니라 `app/ui/components.py`의 모달 다이얼로그
- 선행 검토: `.claude/docs/review/2026-08-11_buyer-review.md`

## 검증

이 작업은 앱 동작을 바꾸지 않으므로 **브라우저 화면 검증 대상이 아니다.** 서버 재시작도 불필요하다. 확인할 것은 다음 3가지:

1. **frontmatter 파싱** — `.claude/agents/customer-pm.md`가 `buyer-review.md`와 동일한 4키 구조인지 육안 대조. `name`이 파일명과 일치하는지 확인.
2. **에이전트 등록** — 실행 시 `customer-pm`이 `subagent_type`으로 호출되는지 확인. 안 되면 위 우회 경로 사용 후 그 사실을 보고.
3. **산출물 형식 준수** — 생성된 md가 사용자가 지정한 8개 항목을 **누락·추가·순서변경 없이** 담고 있는지, "2. 필요 없는 기능"이 양쪽 섹션 모두에서 **실제로 채워졌는지**(회피 방지 규칙이 작동했는지) 확인.
