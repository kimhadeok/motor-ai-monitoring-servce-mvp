# 알림 발송을 AI 진단·리포트 생성보다 앞으로 (2026-08-13)

## Context

현재 확정 규칙은 DANGER/FAULT 도달 시 **AI 에이전트 가동 → 진단 → 리포트 HTML 생성·저장 → 담당자 알림 발송** 순이다(`03_state_event_logic.md` §4.1).

사용자 지적: 문자·카카오 알림톡은 외부 게이트웨이 왕복이라 송수신에 시간이 걸린다. 진단·리포트를 기다렸다가 보내면 담당자 인지가 그만큼 늦어진다. **알림을 먼저 보내고 진단·리포트를 그 뒤에 생성**하도록 바꾼다.

근거상 문제가 없다 — 알림 문구는 `build_notification_message(motor_id, status, trigger_reason)`으로 만들어지며 **진단 결과를 필요로 하지 않는다**([diagnosis.py:217](app/services/diagnosis.py:217)). 상태 전이 로그만 있으면 즉시 발송 가능하다.

측정된 비용: 리포트 1건 생성 4.12초(진단 LLM 3.7초 + SOP 임베딩 0.3초), 프로세스 첫 건은 langgraph 콜드 import 포함 5~9초(`02 §2.4.1`). 종전 순서에서는 이 시간만큼 담당자 통보가 밀렸다.

**알림 문구는 바꾸지 않는다** (2026-08-13 사용자 확정). 알림 직후 자동으로 리포트가 생성되므로 "리포트를 확인하세요"는 그대로 유효하다.

**부수 효과 — 문서가 현재 구현에 오히려 가까워진다.** 시드는 전이 시각 그대로 알림을 발행하고([seeding.py:443](app/services/seeding.py:443)), 리포트 HTML은 최초 열람 시 생성된다(`02 §6.1.1`). 즉 실제 데이터 흐름은 이미 "알림 먼저, 리포트 나중"이다. 종전 문서가 이를 뒤집어 서술하고 있었고, 그 어긋남을 리포트 타임라인이 +12초 오프셋으로 덮고 있었다.

## 새 규칙

```
DANGER/FAULT 전이 확정
  → 쿨다운(§5) 판정
  → 담당자 알림 발송 (문자 기본 + 이메일 동반, 채널마다 기록 1행)
  → AI 에이전트 가동 (단기 2h + 장기 6h + RAG 매뉴얼 결합 진단)
  → 리포트 HTML 생성·저장
```

쿨다운은 순서와 무관하게 동일하다 — 통과하지 못하면 알림과 에이전트 가동이 함께 차단되고 로그만 적재된다. 다만 **쿨다운 판정을 알림 발송 앞에서 한다**는 점을 명시한다.

**L159 규칙 반전이 핵심이다.** 현재: *"타임라인의 발송 시각은 리포트 생성 시각(이벤트+12초)을 쓰고 `notification_logs.created_at`은 쓰지 않는다 — 그대로 표시하면 알림 발송이 AI 진단 완료보다 앞서는 어긋난 순서가 된다."*

새 순서에서는 그 "어긋남"이 **정상 순서**가 된다. 따라서 **`notification_logs.created_at`을 그대로 쓴다**로 뒤집고, 이유를 적는다: §2.5의 원칙("리포트는 실제 기록보다 많은 말을 하지 않는다")에 맞고, 표시용 오프셋 규칙이 하나 줄어든다. 감지 시각과 같은 초로 찍히는 것은 **정상** — 감지 즉시 발송이기 때문이다. +12초 오프셋은 이제 "AI 진단 완료 / 리포트 생성" 줄에만 남는다.
