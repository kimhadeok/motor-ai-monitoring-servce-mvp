# 03. 상태 관리 및 이벤트 처리 로직 명세

> 원본: `.claude/docs/user/모터 AI 니터링 시스템 아키텍처.md`, `.claude/docs/user/전체 시스템 아키텍처 흐름도.md`, `.claude/docs/user/AI 에이전트 아키텍처 상세 설계.md`, `.claude/docs/user/테이블 설계.md`
> 참고: `02_architecture.md`의 확정 파라미터(단기 2시간 / 장기 6시간 / 쿨다운 1시간)를 이 문서에서 구체적인 로직으로 전개함
> 작성: coreagent · 상태: 확정

## 1. 4단계 상태 정의

| 상태 | 의미 | 판정 기준 |
|---|---|---|
| NORMAL | 정상 운전 | `값 < warning_range` |
| WARNING | 주의 | `warning_range ≤ 값 < danger_range` |
| DANGER | 위험 | `danger_range ≤ 값 < fault_range` |
| FAULT | 고장/정지 | `값 ≥ fault_range` |

임계값은 모터별로 `motors` 테이블(`normal_range`, `warning_range`, `danger_range`, `fault_range`)에 저장된 값을 사용 (`04_database_schema.md` 연계).

## 2. 판정 단위 — 지표별 상태 vs 모터 대표 상태 (보강)

원본 문서들은 "모터 상태"를 단일 값처럼 서술하지만, `motor_telemetry` 테이블은 온도/진동/전류/소음 **4개 지표를 각각** `temp_status`, `vib_status`, `current_status`, `sound_status`로 개별 판정하도록 설계되어 있음. 반면 `화면구성.md`의 메인 대시보드는 모터 1개당 상태값 1개("WARNING + 일시")만 표시함 — 이 둘을 잇는 집계 규칙이 원본에 없어 보강함.

**제안 규칙**: 모터의 대표 상태 = 4개 지표 상태 중 **가장 심각한 단계**
```
심각도 순위: FAULT > DANGER > WARNING > NORMAL
motor_status = max(temp_status, vib_status, current_status, sound_status)  # 심각도 기준
```
- 상태 전이 감지, 쿨다운, AI 에이전트 트리거는 **지표(metric) 단위**로 개별 수행 (근거: `motor_status_logs.metric_name` 컬럼 존재)
- 대시보드/이벤트 리스트에는 모터 단위 대표 상태로 표시

## 3. 상태 전이 감지 및 이벤트 발행 규칙

- 감시 대상: `(motor_id, metric_name)` 쌍 단위로 직전 상태와 현재 상태를 비교
- **전이(Transition)가 발생한 경우에만** 처리 (동일 상태 반복/수치 흔들림은 무시 → 핑퐁 방지)
- 전이 1건당 이벤트 정확히 1개만 발행
- MVP 발행 방식: `02_architecture.md` §3에서 확정한 대로 별도 브로커 없이 인메모리 함수 호출(또는 경량 폴링)로 트리거

## 4. 상태별 처리 로직

원본 문서는 "NORMAL→WARNING", "WARNING→DANGER" 같은 **인접 단계 전이만** 서술하고 있음. 그러나 실제로는 10~30초 주기 폴링 특성상 한 주기 사이에 단계를 건너뛰는 급변(예: 정상 상태에서 갑자기 FAULT급 수치로 튐), 그리고 반대로 심각한 상태에서 값이 낮아지는 회복 전이도 발생 가능함. 이를 모두 다루기 위해 **인접 전이 나열 방식 대신, 도달한 상태(도착 상태) 기준의 일반 규칙**으로 정리하고(보강), 아래에 구체적 케이스 표를 붙임.

### 4.1 일반 규칙 (도착 상태 기준)

| 도착 상태 | 처리 (출발 상태와 무관하게 동일 적용) |
|---|---|
| WARNING | 로그만 적재 (전조 증상 컨텍스트 축적). AI 에이전트 미가동, 리포트 미생성 |
| DANGER | 쿨다운(§5) 통과 시 AI 에이전트 가동 → 단기(2h)+장기(6h) 데이터 + RAG 매뉴얼 결합 진단 → PDF 리포트 생성 → 담당자 알림 발송 |
| FAULT | DANGER와 동일 자동 대응 (쿨다운 통과 시 에이전트 가동 → 리포트 생성 → SMS/이메일 알림). FAULT는 이미 설비 문제가 발생한 상태이므로 자동 처리 |
| NORMAL (회복) | 로그만 적재 (회복 이력 추적용). 알림/에이전트 가동 없음 |

**보강 근거**: 몇 단계를 건너뛰었는지(예: NORMAL→DANGER처럼 2단계 스킵) 자체는 `02_architecture.md`에서 정의한 "돌발 vs 점진적 악화 판정"의 근거 데이터로 활용 가능 — 에이전트 진단 시 "직전 기록 상태 → 현재 상태" 낙차 정보를 함께 전달하는 것을 제안.

### 4.2 케이스별 상세

| 구분 | 예시 전이 | 처리 |
|---|---|---|
| 단계적 악화 | NORMAL→WARNING, WARNING→DANGER, DANGER→FAULT | §4.1 일반 규칙대로 처리 |
| 스킵 악화 (급변) | NORMAL→DANGER, NORMAL→FAULT, WARNING→FAULT | 도착 상태 기준 규칙 그대로 적용 (예: NORMAL→DANGER는 "DANGER" 규칙 적용, 즉 에이전트 즉시 가동). 로그의 `trigger_reason`에 "급변(단계 스킵)" 표시 제안 |
| 단계적 회복 | WARNING→NORMAL, DANGER→WARNING | §4.1 "NORMAL(회복)" 또는 로그만 적재 규칙 적용 |
| 스킵 회복 | DANGER→NORMAL | 로그만 적재. 단, 급격한 개선은 센서 오류 가능성도 있어 로그에 "스킵 회복 — 센서 점검 권장" 플래그 제안 (보강) |
| **FAULT → 하위 상태 (정비 후 재가동)** | FAULT→DANGER, FAULT→WARNING, FAULT→NORMAL | 일반 회복 규칙과 다르게 취급 제안 (§4.3 참고) |
| **데이터 미수신 (통신 두절)** | 상태 전이 아님 — 신규 케이스 | §4.4 참고 (보강, 원본에 없던 케이스) |

### 4.3 FAULT 이후 복구 처리 (보강 — 별도 확인 필요)

FAULT는 설비가 이미 정지/고장난 상태이므로, 센서 수치가 낮아졌다고 자동으로 "복구됨"으로 처리하는 것은 위험할 수 있음(예: 정비 전 일시적 수치 하락). `report_template.html`의 SOP에도 "시운전 확인 후 AI 에이전트 세션 리셋(Thread Reset)" 절차가 명시되어 있어, 이는 자동이 아닌 **사람의 확인 절차**를 전제하는 것으로 보임.

**제안**: FAULT 상태의 모터는 센서 수치가 하락해도 시스템이 자동으로 WARNING/NORMAL로 전환하지 않고, **"정비 완료 확인 대기"** 상태를 유지. 담당자가 대시보드에서 수동으로 "정비 완료" 처리(세션 리셋)해야 이후 정상적인 자동 상태 판정이 재개됨.

### 4.4 데이터 미수신 / 통신 두절 (보강 — 원본에 없던 신규 케이스)

`전체 시스템 아키텍처 흐름도.md`의 백그라운드 프로세스 항목("값이 등록되고 있는지 확인")에서 착안. 모터의 수집 주기(10/20/30초) 대비 일정 횟수 이상 데이터가 들어오지 않으면, 센서/통신 이상으로 간주.

**제안**: 연속 3주기 이상 미수신 시 "통신 두절" 알림을 담당자에게 발송 (기존 4단계 상태와는 별개의 알림 유형). 이 값 판정을 위한 저장 위치는 `04_database_schema.md`에서 반영 여부 결정 필요.

## 5. 쿨다운 타임 적용 (보강 — 적용 범위 제안)

- 적용 기준값: `02_architecture.md` 확정값 — 전이 종류 무관 **1시간**
- **적용 범위(제안)**: `(motor_id, metric_name)` 단위로 독립 적용. 즉 한 모터의 온도 지표가 쿨다운 중이어도 같은 모터의 진동 지표 전이는 별도로 즉시 처리됨 (근거: `motor_status_logs`가 지표별 로그이므로)
- 쿨다운 중 동작: 신규 **AI 에이전트 재가동 및 알림 발송만 차단**. 로그 자체는 계속 적재하여 트렌드 데이터 손실 방지 (원본에 명시 없어 제안)

## 6. 슬라이딩 윈도우 데이터 관리 (MVP 구현 방식 제안)

원본은 "에이전트가 최근 N시간 데이터를 메모리에 들고 다닌다"는 개념(슬라이딩 윈도우/버퍼)으로 서술되어 있으나, MVP 스택은 SQLite 단일 DB 구조(`01_tech_stack.md`)이므로 별도의 인메모리 캐시 계층을 두지 않고 **매 진단 시점에 SQLite에서 최근 2시간/6시간 데이터를 조회**하는 방식을 제안:

```
단기 버퍼 데이터 = SELECT * FROM motor_telemetry
                    WHERE motor_id = ? AND time >= NOW() - 2h
장기 트렌드 데이터 = SELECT * FROM motor_telemetry
                    WHERE motor_id = ? AND time >= NOW() - 6h
```
정식 서비스 확장 시 조회 성능이 문제가 되면 인메모리 캐시(Redis 등) 도입 검토.

## 7. 확정 사항 (보강/제안 항목 확인 결과)

1. **지표별 vs 모터 대표 상태 집계 규칙 (§2)**: coreagent 제안대로 확정 — 4개 지표 중 가장 심각한 단계를 모터 대표 상태로 사용.
2. **쿨다운 적용 범위 (§5)**: coreagent 제안대로 확정 — `(motor_id, metric_name)` 단위 독립 적용.
3. **FAULT 상태의 리포트 생성 방식**: DANGER와 동일하게 **자동으로** AI 에이전트 가동 + 리포트 생성 + SMS/이메일 알림 발송으로 확정 (§4 반영). FAULT는 이미 설비 문제가 발생한 상태이므로 담당자 수동 요청을 기다리지 않음.

## 8. 신규 보강 항목 확정 (§4 확장분)

4개 항목 모두 coreagent 제안대로 확정:

1. **스킵 악화 처리 (§4.2)**: NORMAL→DANGER처럼 단계를 건너뛴 전이도 도착 상태 기준 규칙을 그대로 적용(예: 즉시 에이전트 가동), 로그에 "급변" 표시.
2. **스킵 회복 처리 (§4.2)**: DANGER→NORMAL처럼 큰 폭으로 값이 낮아지는 경우 "센서 점검 권장" 플래그 기록.
3. **FAULT 이후 복구 절차 (§4.3)**: 센서 수치 하락만으로 자동 복구 처리하지 않고, 담당자가 대시보드에서 수동으로 "정비 완료" 처리해야 정상 모니터링 재개. → **`05_ui_screens.md` 작성 시 정비 완료 처리 버튼 반영 필요**
4. **데이터 미수신/통신 두절 알림 (§4.4)**: 연속 3주기 미수신 시 별도 "통신 두절" 알림 발송. → **`04_database_schema.md` 작성 시 저장 방식 반영 필요**
