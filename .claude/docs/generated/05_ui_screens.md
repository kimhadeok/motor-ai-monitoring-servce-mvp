## 2. 로그인 페이지

- 입력: 이메일(ID) + 비밀번호 (`company_contacts.email`, `password_hash` 대조)
- 부가 검증: 접속 IP가 `company_contacts.allowed_ip`에 값이 있는 경우 해당 IP만 허용 (MAC 주소 체크는 미적용 — §5-1 참고)
- 로그인 시도는 성공/실패 관계없이 `login_logs`에 기록 (성공 시 `contact_id` 채움, 실패 시 NULL 허용)
- 성공 시 메인 대시보드로 이동

**화면 구성 확정 (2026-08-05)** — 기존에는 동작 규칙만 정의돼 있어 구현이 제목과 입력칸 2개로 끝나 있었다. 이 화면은 **고객이 서비스를 처음, 그리고 로그인 전에는 유일하게 마주하는 화면**이므로 무엇을 해주는 서비스인지가 드러나야 한다.

위에서부터 네 부분으로 구성한다.

1. **서비스 소개** — 아이콘 + 서비스명 + 한 줄 설명. 값은 `config.SERVICE_NAME` / `SERVICE_ICON` / `SERVICE_TAGLINE`.
2. **로그인 폼** — 이메일·비밀번호·로그인 버튼.
3. **시연용 계정 안내** — `st.expander`로 접어 둔다. 펼치면 계정 목록과 공통 비밀번호가 나온다. 계정 목록은 **DB에서 조회**한다(`list_demo_accounts()`) — 화면에 하드코딩하면 시드 구성이 바뀔 때 안내와 실제가 어긋난다.
4. **핵심 기능 3가지** — 실시간 감시 / AI 진단 / 리포트 자동 생성. 값은 `config.SERVICE_HIGHLIGHTS`.

- **폭 제한**: `main.py`가 대시보드 기준으로 `layout="wide"`를 쓰기 때문에, 그대로 두면 폼이 화면 전체 폭으로 늘어져 더 휑해 보인다. `st.columns([1, 2, 1])`의 가운데 열에 배치한다.
- 시연 관점: 계정 안내가 화면에 없으면 시연 자리에서 README를 찾아봐야 로그인할 수 있다. 접어 두는 것은 평소 화면을 깔끔하게 유지하기 위한 절충이다.

**계정 자동 입력 (2026-08-05 추가)** — 시연·개발 중 매번 계정을 타이핑하지 않도록 폼을 미리 채운다.

- **첫 진입 시에만** 첫 데모 계정과 공통 비밀번호를 채운다. 사용자가 지운 값은 다시 되살리지 않는다 — 다른 계정을 직접 입력하려 할 때 방해가 되기 때문이다.
- 시연용 계정 목록의 각 행에 **[채우기] 버튼**을 둔다. demo1 ↔ demo2를 오갈 때 다시 타이핑하지 않아도 된다.
- `config.PREFILL_DEMO_CREDENTIALS`로 끈다. **실제 서비스 배포 시 `False`로 바꾼다.**
- **구현 주의**: [채우기] 버튼은 폼 아래에 있어 클릭 시점에 위젯 key의 `session_state`를 바꿀 수 없다(`StreamlitAPIException: cannot be modified after the widget ... is instantiated`). 버튼은 요청만 별도 세션 키에 남기고, **스크립트 최상단(위젯 생성 전)** 에서 값을 채운다.

## 2-1. 공통 상단 헤더 (2026-08-05 확정)

로그인 후 모든 페이지 최상단에 둔다. **사이드바는 사용하지 않는다.**

```
⚙️ 모터 AI 모니터링                          (주)한국모터스
                                                  김철수   [로그아웃]
───────────────────────────────────────────────────────────
```

- **좌측**: 서비스 아이콘 + 서비스명. 로그인 화면(§2)에서 세운 브랜드가 로그인 후에도 이어진다.
- **우측**: `회사명`(굵게) + `담당자명`(작게), 세로 구분선, 테마 안내(§5-5), 로그아웃 버튼. 담당자가 지금 어느 회사 계정으로 보고 있는지 늘 확인할 수 있다.
- 회사명은 로그인 시 `company_contacts ⨝ companies` 조회 결과를 세션(`company_name`)에 담아 재사용한다. 매 화면 표시되는 값이라 페이지마다 다시 조회하지 않는다.

**컬럼 구성**: `st.columns([4.6, 4.2, 1.2])` — 브랜드 / 로그인 정보+테마 / 로그아웃.

**로그인 정보와 테마 안내는 한 `st.markdown` 블록에 함께 담는다.** 별도 컬럼으로 나누면 폭이 좁아질 때 한쪽이 밀려 다른 쪽 자리를 차지한다(실제로 4컬럼 구성에서 회사명이 사라지고 그 자리에 테마 안내가 표시되는 문제가 발생했다). 같은 flex 컨테이너에 두면 폭이 부족할 때 회사명이 말줄임으로 줄고 테마 안내는 `flex: 0 0 auto`로 고정된다.

**사이드바를 쓰지 않는 이유**: 일반 웹 서비스의 상단 헤더 형태가 담당자에게 익숙하고, 좁은 사이드바에 담당자명과 로그아웃만 두면 공간 낭비가 크다. 페이지 이동은 `st.navigation(position="hidden")`으로 목록을 감추고, 아래 방식으로 처리한다.

- **메인 페이지 간 이동(메인 대시보드 / 모터 그래프 / 모터 현황)**: 헤더 하단에 페이지 이동 내비 버튼 3개를 둔다(2026-08-06 추가). 현재 페이지는 primary 버튼으로 강조한다. 목록은 `navigation.HEADER_NAV_PAGES`, 렌더는 `components._page_nav()`. `page_header(active=...)`로 활성 페이지를 넘긴다.
- **상세로 진입**: 모터 카드/현황 카드의 클릭(카드 전체가 클릭 영역), 이후 상세 페이지의 [← 대시보드] 버튼으로 복귀.

§3.1 컨텍스트 줄에서는 회사명을 뺀다 — 헤더와 중복되기 때문이다.

## 3. 메인 대시보드

### 3.1 상단 — 회사/현황 정보

| 표시 항목 | 데이터 출처 |
|---|---|
| 회사 정보 | `companies` (로그인한 담당자의 `company_id` 기준) |
| 등록된 모터 수 | `motors` count (해당 company_id) |
| 서비스 시작 일자 | `companies.created_at` |
| 총 운영 일수 | `오늘 - companies.created_at` (일 단위, 보강: 계산식 명시) |
| 상태별 모터 수 (NORMAL 제외) | 각 모터의 **대표 상태**(`03_state_event_logic.md` §2 — 4개 지표 중 최고 심각도) 기준 WARNING/DANGER/FAULT 개수 집계 |

**배치 확정 (2026-08-05)** — 위 5개 항목은 모두 표시하되, **매일 확인할 값과 아닌 값을 분리**한다.

담당자가 아침에 대시보드를 여는 이유는 "지금 문제 있나, 있으면 뭘 해야 하나"이지 계약 정보 확인이 아니다. 회사명·모터 수·서비스 시작일·운영 일수를 `st.metric` 타일 4칸에 쓰면, 정작 답이 필요한 질문이 화면에서 사라진다.

- **컨텍스트 줄 (캡션 1줄)**: `(주)한국모터스 · 모터 3대 · 서비스 시작 2025-06-19 (412일째)` — 회사 정보, 등록된 모터 수, 서비스 시작 일자, 총 운영 일수를 여기에 모은다.
- **요약 타일 4칸**: 운영 질문에 답하는 값만 둔다.

| 타일 | 값 | 보조줄 | 답하는 질문 |
|---|---|---|---|
| 조치 필요 | DANGER + FAULT 모터 수 | `고장 n · 위험 n` | 지금 손대야 할 설비가 있나 |
| 주의 관찰 | WARNING 모터 수 | `정상 n대` | 지켜봐야 할 설비가 있나 |
| 최근 24시간 이벤트 | 전이 건수 | `악화 n · 회복 n` | 밤사이 무슨 일이 있었나 |
| 마지막 수집 | 최신 텔레메트리 시각(상대) | `정상 수집 중` | 데이터는 들어오고 있나 |

- "상태별 모터 수(NORMAL 제외)"는 **조치 필요 / 주의 관찰 두 타일로 나눈다.** 대응 시급성이 다르기 때문이다 — FAULT·DANGER는 지금 조치, WARNING은 관찰이다. 합산해 한 칸에 넣으면 이 구분이 사라진다.
- **내역은 값 아래 보조줄로 표기한다.** `st.metric`의 `delta`는 값이 증감이 아니어도 항상 상승 화살표(`↑`)를 붙인다. `delta_color="off"`는 색만 지울 뿐 화살표는 남아, `↑ 정상 7대`·`↑ 정상 수집 중`처럼 늘어난 것으로 오해되는 표시가 나온다(2026-08-05 확인).

**타일 자체 렌더링으로 전환 (2026-08-07 변경).** `st.metric`을 버리고 `components.summary_tiles()`가 그리는 카드로 바꿨다. 화면 첫 화면인데 라벨·값·보조줄이 아무 테두리 없이 텍스트로만 놓여 무게가 실리지 않았고, `.metric-sub`를 음수 마진으로 끌어올려 붙이는 방식이라 값과 보조줄 사이 간격도 불안정했다.

- **모터 카드와 같은 언어**로 그린다 — 상단 액센트 3px + 카드 배경 + 테두리(`.summary-tile`). 대시보드 전체가 한 벌로 보인다.
- **액센트 색이 곧 상태다.** 장식이 아니라 정보이므로 숫자를 읽기 전에 색으로 먼저 안다.

| 타일 | 색 규칙 |
|---|---|
| 조치 필요 | 고장이 있으면 FAULT색(빨강), 위험만 있으면 DANGER색(주황), 0대면 NORMAL색 |
| 주의 관찰 | 1대 이상이면 WARNING색, 0대면 NORMAL색 |
| 최근 이벤트 | 브랜드색 고정 (심각도 개념이 없는 집계값) |
| 마지막 수집 | 수집 중이면 NORMAL색, 데이터 없으면 DANGER색 |

- **조치 필요 타일은 고장이 있으면 FAULT색(빨강), 위험만 있으면 DANGER색(주황)이다.** 2026-08-07 팔레트 재정리(§5-3) 전에는 FAULT가 슬레이트라 옆 WARNING보다 흐려 보여 이 타일에서 FAULT 톤을 일부러 뺐었다. 램프가 단조 증가로 바뀌어 그 우회를 걷어냈다.
- 값 글꼴 30px / 라벨 12px / 보조줄 11.5px로 위계를 분명히 한다.
- **열 수는 4열 → (820px 이하) 2×2로 명시한다.** `repeat(auto-fit, minmax(...))`를 쓰면 중간 폭에서 3열이 되어 타일 4개가 3+1로 접히고 마지막 하나만 홀로 남는다.
- 최근 이벤트 창은 `config.DASHBOARD_RECENT_WINDOW_HOURS = 24`.
- "마지막 수집"은 통신 두절 감지(`03_state_event_logic.md` §4.4)가 구현되기 전까지 **데이터 유입 여부를 확인할 유일한 수단**이다.

**조치 배너 (2026-08-05 추가)** — 요약 타일 바로 아래, 모터 카드 위에 둔다. 타일은 "몇 대"만 알려주므로 담당자가 어느 설비인지 찾으려면 카드를 훑어야 한다. 배너는 **설비 이름과 해야 할 일**을 직접 말한다.

| 조건 | 상태색 | 문구 |
|---|---|---|
| 미확인 FAULT 지표 있음 | FAULT | 고장 상태입니다. 정비 후 완료 확인을 해주세요 |
| 대표 상태 FAULT인데 미확인 지표는 없음 | FAULT | 정비 완료 확인을 마쳤지만 여전히 고장 임계를 넘는 값이 들어오고 있습니다 |
| 대표 상태 DANGER | DANGER | 위험 상태입니다. 진단 리포트를 확인해주세요 |

두 번째 행이 필요한 이유: 정비 완료를 확인해도 계측값이 즉시 임계 아래로 내려가지는 않는다. 이때 대표 상태는 FAULT지만 확인 버튼은 사라지므로, 첫 번째 문구를 그대로 두면 "완료 확인을 하라는데 버튼이 없는" 상태가 된다. 담당자가 할 일도 다르다 — 확인이 아니라 **현장 재점검**이다.

**색상 확정 (2026-08-05)** — `st.error`/`st.warning`을 쓰지 않고 §5-3 상태색을 그대로 쓰는 자체 배너(`alert_banner()`)로 그린다.

- `st.error`(빨강)/`st.warning`(노랑) 두 가지뿐이라 DANGER 배너가 노랑으로 나왔다. **카드에서는 DANGER가 빨강인데 배너만 노랑이면 담당자가 심각도를 잘못 읽는다.**
- **배너는 상태에 관계없이 같은 형태(좌측 테두리 + 옅은 배경)를 쓴다.** 종전에는 FAULT만 배경을 채웠는데, 상태색이 슬레이트라 테두리만으로는 아래 DANGER 배너보다 약해 보였기 때문이다. 2026-08-07 팔레트 재정리(§5-3)로 FAULT가 램프 최상단(빨강)이 되어 채움 우회를 걷어냈다 — 심각도는 색이 말한다.
- **정비 완료 확인 안내 (2026-08-06 재설계)**: 미확인 FAULT 목록은 상태색 단색 배너 대신 **🔧 아이콘 + 밝은 강조 박스**("정비 완료 확인 필요 — N대가 고장(FAULT)…")로 부각한다(짙은 단색은 '건조'해 조치 요구로 읽히지 않는다). 그 아래 **모터별 카드**(이름·모델명·설치 위치)를 나열하고 각 카드 **안에 작은 [정비 완료 확인] 버튼**을 둔다 — 어느 설비의 버튼인지 카드가 바로 위에서 알려준다. `render_maintenance_confirm()`, 확인은 §4.3 다이얼로그로 이어진다.
- 대표 상태 집계는 §3.2 카드용으로 이미 조회한 모터 목록을 재사용한다. 대표 상태 판정에 지표별 최신 로그 조회가 필요해 따로 계산하면 중복 비용이 든다.
- **시드 데이터가 `companies.created_at`·`motors.created_at`을 명시적으로 채운다.** DB 기본값(현재 시각)에 맡기면 "총 운영 일수"가 항상 0일이 되고 §4.1 등록일자도 전부 오늘이 되어, 두 항목이 시연에서 아무것도 보여주지 못한다. 회사별로 다른 값을 주며 모터 등록일은 소속 회사의 서비스 시작일보다 뒤가 되도록 한다.

### 3.2 모터별 카드

```
[모터 이미지] --> [API 이미지] --> [AI Agent 아이콘]
   모터 모델명
   [상태 배지: WARNING]
   26/07/01 13:05
```

- 모터 이미지 → API → AI Agent 흐름을 "데이터가 흐르는 것처럼" 애니메이션 표시
  - 구현: `01_tech_stack.md` §2.5에서 확정한 커스텀 CSS 애니메이션 또는 `streamlit-lottie` 사용
- 상태 배지: 모터 대표 상태 + 최근 상태 변경 일시(`motor_status_logs` 최신 `created_at`)
- 상태별 색상 (보강 — report_template.html과 통일된 팔레트 재사용, 아래 §4 참고)
- 카드 클릭 시 모터 상세 페이지로 이동

**구현 확정 (2026-08-05)**

- **카드 전체가 클릭 영역이다 (2026-08-05 확정)**. Streamlit은 임의 HTML 요소에 콜백을 붙일 수 없으므로, 카드와 같은 컨테이너에 버튼을 두고 **CSS로 카드 위를 투명하게 덮는다**. 위젯 `key`가 DOM에 `st-key-{key}` 클래스로 노출되는 것을 이용해 `[class*="st-key-motorclick-"] button { opacity: 0 }`으로 잡는다. 클릭 시 `selected_motor_id`를 세션에 담고 `st.switch_page`로 이동한다.
  - **링크(`<a href="?motor=...">`) 방식은 쓸 수 없다.** `target="_self"`를 붙여도 브라우저가 페이지를 새로 로드하고, 그러면 Streamlit 세션이 새로 만들어져 `session_state`가 비워진다 — 로그인 상태가 풀려 로그인 화면으로 돌아간다. 실제로 이 방식을 먼저 시도했다가 확인한 문제다.
  - 버튼 라벨은 `"{모터명} 상세 보기"`로 둔다. 화면에는 보이지 않지만 스크린리더에는 읽혀 접근성이 유지된다.
  - 클릭 가능함을 알리기 위해 hover 시 카드가 살짝 떠오르고 테두리가 상태색으로 바뀌며, 카드 우하단에 `상세 보기 ›` 안내를 둔다. `prefers-reduced-motion` 환경에서는 이동 효과를 끈다.
- **카드 안에는 위젯을 두지 않는다.** 카드 전체가 클릭 영역이라 내부 버튼과 클릭이 겹치고, 카드마다 버튼 유무가 달라지면 높이도 어긋난다. FAULT 모터의 정비 완료 확인은 §3.1의 **정비 완료 확인 안내(모터별 카드)** 에서 처리한다.

**그리드 (2026-08-05 확정)**

- 한 행에 `config.MOTOR_CARD_COLUMNS = 5`개. COMP-002(10대)는 2행이지만 **COMP-001은 200대라 카드 그리드가 40행으로 매우 길고 무겁다** — 전체 조망은 모터 현황(§3-B) 페이지가 맡는다.

**표시 개수 제한 (2026-08-07 임시, 개수 추후 확정)** — `config.DASHBOARD_MOTOR_CARD_LIMIT`(현재 20)개만 그린다. `None`이면 제한 없이 전부 그린다.

- **심각도 순으로 고른다** (`services.motors.select_priority_cards()`). `list_company_motors()`는 등록 순(motor_id)을 유지하지만 앞에서부터 그냥 자르면 안 된다 — COMP-001은 200대 중 조치 필요가 17대이고 motor_id 순으로는 앞쪽에 거의 들어오지 않아, **문제를 발견하라고 있는 화면이 문제를 전부 가리게 된다.**
- 같은 상태끼리는 등록 순을 유지한다(안정 정렬). "설비가 늘 같은 자리에 있어야 담당자가 위치로 기억한다"는 원래 의도를 그 안에서 지킨다.
- 카드 위에 캡션으로 `조치가 급한 순으로 N대만 표시합니다 (전체 M대 · 목록 전체는 '모터 현황' 페이지에서…)`를 둔다. 일부만 보고 있다는 사실을 화면이 직접 말해야 한다.
- **상단 요약(§3.1)과 조치 배너는 제한 이전의 전체 목록으로 계산한다.** 집계와 배너의 설비 이름은 200대 기준 그대로다.
- **성능 개선은 아니다.** `list_company_motors()`는 여전히 200대 전부에 대해 모터당 쿼리를 돈다. 줄어든 것은 렌더링(무거운 SVG 카드)뿐이며, 쿼리까지 줄이는 것은 `remaining_work.md #7`에 남아 있다.
- 행 사이 간격은 `config.MOTOR_CARD_ROW_GAP_PX = 16`. **카드가 아니라 컬럼 블록의 `margin-bottom`에 준다.** 클릭 버튼이 `inset: 0`으로 블록을 덮으므로 카드에 margin을 주면 간격까지 클릭 영역이 된다. margin은 요소 박스 밖이라 블록 크기가 변하지 않아 카드 사이 빈 공간을 눌러도 반응하지 않는다.

**세로 길이 고정 (2026-08-05 확정)** — 카드마다 높이가 달라 그리드가 들쭉날쭉해지는 문제를 다음으로 해결한다.

원인은 두 가지였다. ① 이상 지표는 값 글꼴이 14px → **18px**로 커져 그 행만큼 아래가 밀린다. ② 5열이라 카드가 좁아 모터명·설치 위치가 **모터마다 다른 줄 수로 접힌다**.

카드 전체에 `height`를 주면 내용이 잘리므로 **구성 요소별로 높이를 고정**한다.

| 요소 | 높이 | 넘침 처리 |
|---|---|---|
| 모터명 + 배지 | 22px | 말줄임 |
| 모델명 · 설치 위치 | 30px | 최대 2줄 clamp |
| 지표 이름/값 행 | 21px | 말줄임 |
| 게이지 | 7px | — |
| 지표 설명 줄 | 14px | 말줄임 |
| 추이 영역 | 스파크라인 높이 + 10px | — |
| 하단 변경 시각 | 16px | 말줄임 |

- 이상 지표는 **글꼴만 키우고 `line-height`는 고정 행 높이(21px)를 그대로 쓴다.** 그래야 강조하면서도 아래를 밀지 않는다.
- **설명 줄은 모든 지표에 둔다.** 이상일 때만 넣으면 카드마다 줄 수가 달라진다. 정상 지표는 `고장 임계의 N%`로 채우며, 덤으로 여유가 얼마인지 읽힌다.
- 이상 카드에 **그림자를 주지 않는다.** 크기는 그대로여도 시각적으로 카드가 커 보여 정상 카드와 달라 보인다. 구분은 상단 3px 테두리 색과 옅은 배경색만으로 한다.
- **흐름 애니메이션은 커스텀 CSS로 구현한다** (§2.5의 두 선택지 중 CSS 확정). `streamlit-lottie`는 애니메이션 JSON을 외부에서 받아와야 해 오프라인·CSP 제약이 있는 반면, CSS 키프레임은 추가 의존성과 네트워크 요청이 전혀 없다.
  - 구조: `⚙️ 모터 —— 🔌 API —— 🤖 AI Agent`. 두 연결선의 배경 그라데이션을 흘려보내 데이터 이동을 표현하고, 두 번째 선은 반 주기 늦게 출발시켜 흐름 방향이 드러나게 한다.
  - 색상은 모터 대표 상태를 따른다(`STATUS_COLORS`를 CSS 변수 `--flow-color`로 주입).
  - 주기는 `config.DATA_FLOW_ANIMATION_SECONDS`, 노드 구성은 `config.DATA_FLOW_NODES`로 중앙화한다.
  - `prefers-reduced-motion: reduce` 환경에서는 애니메이션을 정지시킨다.

### 3.3 이벤트 발생 내역 리스트

- 컬럼: 발생 일시, 모터명, 상태 변화, **값 변화**, 발생 사유, 리포트 버튼. 폭은 `config.EVENT_COLUMN_WIDTHS_WITH_MOTOR`.
- 데이터 출처: `motor_status_logs` (모터 대표 상태 기준 전이 이벤트, 최신순)
- 최근 **최대 10개** 표시

**결과 상태 필터 (2026-08-07 추가)** — `config.DASHBOARD_EVENT_STATUSES`(현재 `FAULT`, `DANGER`)에 해당하는 전이만 싣는다. `None`이면 전체를 보여준다.

- 대시보드는 "지금 손대야 할 것"에 답하는 화면이다. `NORMAL → WARNING` 같은 **관찰 단계 전이가 섞이면 조치가 필요한 건이 10칸 안에서 밀려난다.**
- **필터는 화면이 아니라 조회에서 건다.** `LIMIT`이 필터보다 먼저 걸리면 최근 10건이 전부 관찰 단계일 때 조치 대상이 한 건도 안 보인다.
- **필터가 걸렸다는 사실을 캡션이 직접 말한다** — `고장 · 위험 전이 N건 · 주의(WARNING)를 포함한 전체 이력은 모터별 상세 페이지에서…`. 안 그러면 WARNING 전이가 없는 것을 데이터 누락으로 오해한다. 빈 목록일 때도 `최근 고장 · 위험 이벤트가 없습니다`로 범위를 밝힌다.
- 이 필터 덕에 **모든 행에 리포트 버튼이 붙는다** — 버튼 노출 조건(`DANGER`/`FAULT`)과 같은 범위이기 때문이다.
- 상태 한글 표기는 `config.STATUS_KOREAN_LABELS`를 쓴다(알림 문구와 공유).

**값 변화 컬럼 (2026-08-07 추가)** — `94.73 → 95.12 dB` 형태로 계측값의 변화를 함께 보여준다.

상태 전이는 "어느 상태에서 어디로"만 말하고 **"얼마였다가 얼마가 됐는지"는 말하지 않는다.** 담당자가 급한 정도를 가늠하려면 수치가 필요하다 — 임계를 아슬하게 넘었는지, 크게 뛰었는지에 따라 대응이 다르다.

- **데이터**: 이벤트 시각의 `motor_telemetry` 행에서 해당 지표 값(현재), 그 직전 수집 행에서 같은 지표 값(이전). `metric_name`이 행마다 다르므로 SQL `CASE`로 컬럼을 고르고, 이전 값은 상관 서브쿼리로 가져온다(`services/events.py`). `(motor_id, time DESC)` 인덱스를 탄다.
- **소수점 자릿수**: 기본 **2자리**(`config.EVENT_VALUE_DECIMALS`). **두 값이 같게 찍히면 구분될 때까지 최대 3자리 더 늘린다** — 임계 바로 앞뒤에서 전이가 일어나면 반올림에 묻혀 임계를 넘은 사실이 사라진다(실측: 진동 `5.97 → 6.03`이 1자리에서는 `6.0 → 6.0`).
- **표기**: 이 열의 값 글꼴을 **15px**로 리스트에서 가장 크게 둔다. 담당자가 급한 정도를 판단하는 수치이기 때문이다. 이전 값은 흐리게, 현재 값을 굵게(800) 해 시선이 "지금 얼마인가"에 먼저 간다. 화살표는 악화(DANGER색)·회복(NORMAL색)으로 물들인다.
- **값이 없을 때**: 첫 수집이라 이전 값이 없거나 계측 컬럼이 없는 지표(`connectivity`, `03 §4.4`)는 있는 쪽만 표시하고, 둘 다 없으면 `-`로 둔다. 빈칸으로 두면 데이터가 누락된 것처럼 보인다.

**행 구분선과 열 폭 (2026-08-07)** — 열이 6개로 늘면서 어느 값이 어느 행인지 눈으로 따라가기 어려워졌다.

- **구분선**: 헤더 아래 2px, 행마다 1px. `:has(.event-th)` / `:has(.event-when)`으로 **이벤트 행에만** 건다 — 범위를 좁히지 않으면 대시보드의 다른 컬럼 블록까지 선이 그어져 화면 전체가 표처럼 보인다.
- 선 색은 `border`를 쓴다. `border_soft`는 다크에서 surface와 거의 같아 선이 보이지 않는다.
**행 높이 보정 (필수)** — Streamlit이 블록 높이를 실제 콘텐츠보다 작게 보고해, 그대로 두면 **글자가 하단 구분선을 넘어간다.** 헤더와 데이터 행이 증상도 해법도 달라 **따로 처리해야 한다.**

| | 증상 | 해법 |
|---|---|---|
| 데이터 행 | 마크다운 래퍼를 한 줄(16px)로 보고 → 두 줄인 "발생 일시"(32px)가 넘쳐 구분선에 6px까지 달라붙음 | `[data-testid="stMarkdown"]`과 자식 div `height: auto !important` + 행 블록 `align-items: stretch` + 컬럼 `display:flex; align-items:center` |
| 헤더 | 블록을 라벨 글자보다 작게 보고 → 라벨이 구분선 아래로 삐져나옴 | 블록에 `align-items: flex-start; padding-top: 0.5em; min-height: 2.7em` |

- **어느 쪽도 `align-items: center`를 쓰면 안 된다.** Streamlit이 잘못 보고한 작은 상자를 기준으로 정렬하기 때문에, 데이터 행은 콘텐츠가 아래로 밀리고 헤더는 라벨이 구분선에 1px까지 달라붙는다. 헤더는 위에서 시작시키고(`flex-start`) 여백을 직접 준다.
- **헤더에는 `height: auto`가 듣지 않는다.** 오히려 `stMarkdown`이 3px로 무너진다. `padding-bottom`도 블록 높이에 반영되지 않아 `min-height`가 유일하게 통했다. 두 경로가 왜 다르게 동작하는지는 규명하지 못했다(Streamlit 내부 emotion 스타일 차이로 추정, **미확인**).
- **`min-height`·`padding`은 `em`으로 준다.** 라벨 글꼴만 키우고 이 값을 px 고정으로 두면 다시 넘친다(12px→16px로 올렸을 때 실제로 3px 넘쳤다).
- **컬럼명 글꼴은 본문과 같은 16px.** 12px일 때는 표의 머리글이 아니라 작은 주석처럼 읽혀 어느 열이 무엇인지 눈에 들어오지 않았다.
- 실측: 조치 전 헤더 글자 −5px(넘침) · 행 콘텐츠→선 6px → **조치 후 헤더 위 8 / 아래 10px, 행 10px, 넘침 0건**.
- 헤더는 `st.caption` 대신 `.event-th` 마크다운으로 그린다 — caption에는 CSS가 잡을 클래스가 없어 구분선을 걸 수 없다.

| 9개 | 132px | 잘림 400줄 | 잘림 219줄 |
| 10개(기존) | 128px | 잘림 400줄 | — |

- **9개 이상은 불가능하다.** 여백을 최대로 줄여도 400줄 중 219줄이 잘린다.
- 8개도 가능하지만 여백을 압축해야 겨우 맞아 답답하다. **7개로 확정**해 여백을 원래대로 두고 카드에 숨통을 준다.
- **7개 배치의 카드 폭 상한은 172px**다(`7×172+60=1264` ≤ 컨테이너 1270px, 1440 뷰포트 기준). `config.STATUS_CARD_MIN_WIDTH_PX`를 170px로 두면 행 폭 1250px로 20px 여유가 남는다.
- 부수 효과로 **모터명도 말줄임 없이 전부 들어간다** — 모터명 최대 필요 폭이 147px인데 내용 폭이 147px다.

**여백은 균일한 `gap`이 아니라 자리별로 준다.** 균일하게 줄이면 `온도82.2`처럼 라벨과 값이 붙어 한 단어로 읽힌다.

| 자리 | 값 | 근거 |
|---|---|---|
| 라벨 → 값 (`온도` `82.2`) | 4px | 10px 글꼴의 공백 한 칸. 붙으면 한 단어로 읽힌다 |
| 값 → 단위 (`82.2` `°C`) | 2px | 붙어도 수치와 단위로 구분되어 읽힌다 |
| 지표 사이 구분자 (`·`) | 좌우 3px | — |
| 요소 간격 (`sc-metric-line` gap) | 3px | — |

**세 자리 값 대비.** 온도는 100도를 넘을 수 있다. 내용 폭 147px 기준 실측 여유는 다음과 같다.

| 케이스 | 필요 폭 | 여유 |
|---|---|---|
| 현재 데이터 최대 | 131px | 16px |
| 온도 3자리 (`120.5 °C`) | 137px | 10px |
| 4개 지표 전부 3자리 | 142px | 5px |

`.sc-metric-line`에 `overflow: hidden; text-overflow: ellipsis`를 유지해, 이보다 긴 값이 와도 레이아웃이 밀리지 않고 말줄임으로 끝나게 한다.
- 카드 폭은 고정이다(`flex: 0 0`) — 남는 가로 공간을 채우지 않고 열 수만 화면 폭에 따라 준다. 모든 카드가 부분 행에서도 정확히 같은 크기여야 하기 때문이다.

**구현 확정 (2026-08-05)**

- **미확인 FAULT 판정**: 지표별 **최신** `motor_status_logs` 행의 `new_status`가 FAULT이면 미확인으로 본다. 정비 완료 확인이 같은 지표에 새 행을 남기므로, 확인이 끝나면 최신 행이 FAULT가 아니게 되어 자연히 해제된다. (`contact_id IS NULL` 조건을 따로 보지 않아도 같은 결과가 된다.)
- **신규 행의 상태값**: `previous_status = 'FAULT'`, `new_status = 'NORMAL'`. "정비가 끝나 정상 판정부터 다시 시작한다"는 뜻이며, 이후 수집값이 임계를 넘으면 평소대로 전이가 감지된다.
- **대표 상태와의 관계**: 미확인 FAULT 지표가 하나라도 있으면 최신 텔레메트리 값과 무관하게 모터 대표 상태를 **FAULT로 유지**한다 (`03_state_event_logic.md` §4.3).
- **다이얼로그 상태 유지**: 확인 대상을 세션 상태에 담아둔다. 버튼 클릭 여부로만 다이얼로그를 열면 그 안의 체크박스를 누르는 순간 rerun이 일어나 다이얼로그가 닫히고 확인 절차를 마칠 수 없다. 확인·취소 시 세션 키를 지운다.
- **확인 단위는 지표가 아니라 설비 (2026-08-05 변경)**: 한 모터에 FAULT 지표가 여럿이면 지표마다 확인을 반복하게 되는데, 현장에서 "이 설비 정비를 마쳤다"는 것은 한 번의 행위다. 다이얼로그에 대상 지표를 모두 나열하고 한 번의 확인으로 각 지표에 로그를 1건씩 적재한다.
- **대시보드에서도 확인할 수 있다 (2026-08-05 추가)**: §3.2 모터 카드에 같은 버튼을 둔다. 설비가 멈춘 상태에서 가장 급한 조치가 상세 페이지 안에만 있으면 담당자가 두 번 이동해야 한다. 버튼과 다이얼로그는 두 화면이 같은 컴포넌트를 공유한다.

### 4.4 이벤트 발생 내역 리스트

- 컬럼: 발생 일시, 상태 변화, **값 변화**, 발생 사유, 리포트 버튼. 폭은 `config.EVENT_COLUMN_WIDTHS`(모터명 열이 없다 — 이미 이 모터의 페이지다).
- 데이터 출처: `motor_status_logs` (해당 모터 전체 지표 이벤트)
- 페이징: 페이지당 20개
- 대시보드와 **같은 컴포넌트**(`event_list_header` / `event_row`)를 쓴다. 값 변화 규칙도 §3.3과 동일하다.
- **§3.3의 결과 상태 필터는 걸지 않는다.** 이 화면은 이력이므로 `NORMAL → WARNING → DANGER → FAULT`로 **어떻게 악화됐는지 과정이 보여야** 한다. 대시보드에서 걸러진 관찰 단계 전이를 여기서 확인한다.
- 리포트 버튼의 노출 조건과 클릭 동작은 §3.3과 동일하다 (DANGER/FAULT 로그에 노출, PDF 우선 제공하되 불가 시 HTML 표시)

## 5. 확정 사항 (보강/제안 항목)

### 5-1. 로그인 시 MAC 주소 체크 → IP 체크만 적용 (확정)

MAC 주소는 일반 웹 브라우저 요청에서 서버가 확인할 방법이 없어(HTTP 프로토콜 자체의 구조적 제약) 요구사항에서 제외. `company_contacts.allowed_ip` 기반 IP 체크만 적용 (§2 반영 완료).

### 5-2. 실시간 그래프 자동 갱신 방식 → st.fragment(run_every=...) 적용 (확정)

최초 제안한 `streamlit-autorefresh`는 내부적으로 `st.rerun()`을 호출해 **스크립트 전체를 재실행**하는 방식이라 페이지가 커질수록 갱신마다 불필요하게 느려지는 문제가 있음. 대신 Streamlit 1.33+ 내장 기능인 **`st.fragment(run_every="10s")`**로 확정 — 차트/카드 등 갱신이 필요한 영역만 함수 단위로 분리해 해당 부분만 부분 재실행되도록 함(로그인 체크, DB 조회, 다른 카드 렌더링 등 나머지 페이지는 재실행되지 않음). 별도 패키지 설치 불필요. **`01_tech_stack.md` §2.5에도 반영 완료.**

### 5-5. 테마 (라이트 / 다크 / 시스템) — 2026-08-05 확정

**선택 UI는 Streamlit 기본 메뉴를 쓴다.** 우측 상단 `⋮ → Settings → Choose app theme`에 `Use system setting / Light / Dark` 세 가지가 이미 있다.

앱 안에 자체 선택 위젯을 두지 않은 이유는 다음 두 가지를 확인했기 때문이다.

- `st.context.theme`는 **읽기 전용**이고, 테마를 바꾸는 API가 없다 (`st.set_option`도 런타임 변경 불가).
- 따라서 자체 위젯으로는 Streamlit 자체 위젯(버튼·입력창·metric·dataframe·expander·알림 박스)의 색을 바꿀 수 없다. 전부 CSS로 덮어써야 하는데, 그 경우 사용자가 고른 테마와 Streamlit 위젯이 어긋날 위험이 크다.

**구성**

| 계층 | 담당 | 정의 위치 |
|---|---|---|
| Streamlit 자체 위젯 | Streamlit | `.streamlit/config.toml`의 `[theme.light]` / `[theme.dark]` |
| 앱 커스텀 CSS (카드·배지·게이지·헤더·로그인) | 앱 | `config.THEMES` 팔레트 → `app/ui/styles.py`가 주입 |

- 현재 테마는 `app/ui/theme.py`의 `current_theme()`이 `st.context.theme.type`으로 읽는다. 판별 불가 시 `DEFAULT_THEME`("light")로 떨어진다.
- 다크 팔레트는 색을 그대로 어둡게 만들지 않는다. **남색 브랜드색(`#1e3a8a`)은 어두운 배경에서 읽히지 않아 밝은 파랑(`#60a5fa`)으로 대체**하고, 상태색도 채도를 낮추고 밝기를 올려 대비를 확보한다.
- SVG(스파크라인)의 획 색은 CSS 변수를 쓸 수 없어 `palette()`에서 직접 가져온다.
- 리포트 템플릿(HTML/PDF)은 항상 흰 배경이므로 `STATUS_COLORS` 라이트 기준값을 그대로 쓴다 — 테마의 영향을 받지 않는다.

**헤더 안내 (§2-1)**: 앱에서 테마를 바꿀 수 없는 대신, 상단 헤더의 로그아웃 버튼 옆에 현재 테마와 변경 위치를 표시한다.

```
… (주)한국모터스        ☀️ 라이트        [로그아웃]
        김철수      ⋮ 설정에서 변경
```

아이콘·문구는 `config.THEME_LABELS` / `THEME_HINT`, 마우스를 올리면 전체 경로가 `THEME_HINT_TOOLTIP`으로 뜬다. 클릭 동작은 없다 — Streamlit 메뉴를 프로그램으로 열 수단이 없기 때문이다.

**검토했으나 채택하지 않은 방법**

- **Streamlit 위젯 CSS 전면 override + 자체 선택 위젯**: 버튼·입력·metric·dataframe·expander·알림·dialog 등 12종 이상을 직접 칠해야 한다. 얻는 것은 "선택 위치가 앱 안이냐 메뉴냐"의 차이뿐인데(테마 변경은 보통 1회성), 치르는 비용과 깨질 위험이 크다.
- **JS로 localStorage의 테마 값을 바꾸기**: `st.html(unsafe_allow_javascript=True)`로 가능은 하다. 그러나 적용하려면 페이지 리로드가 필요하고, **리로드하면 Streamlit 세션이 새로 만들어져 로그인이 풀린다**(§3.2에서 링크 방식이 실패한 것과 같은 원인). 테마를 바꿀 때마다 로그아웃되므로 쓸 수 없다.

**알려진 한계**: `st.context.theme`는 앱 첫 로드 직후나 테마 전환 직후에 이전 값을 반환할 수 있다(Streamlit 이슈 #11920). 이 경우 커스텀 CSS와 헤더 표기가 한 번의 리런만큼 늦게 따라온다.

### 5-3. 상태별 색상 팔레트 (2026-08-07 재정리)

**녹색 → 앰버 → 주황 → 빨강의 단조 증가 램프.** 심각도가 올라갈수록 색도 세진다.

| 상태 | 라이트 | 다크 | 배경(라이트/다크) |
|---|---|---|---|
| NORMAL | `#16a34a` 녹색 | `#4ade80` | `#f0fdf4` / `#0f2417` |
| WARNING | `#d97706` 앰버 | `#fbbf24` | `#fffbeb` / `#2a2010` |
| DANGER | `#ea580c` 주황 | `#fb923c` | `#fff7ed` / `#2a1a0e` |
| FAULT | `#dc2626` 빨강 | `#f87171` | `#fef2f2` / `#2b1414` |

**종전 FAULT는 슬레이트(`#1e293b` / 다크 `#cbd5e1`)였다.** "위험(적색)"과 "정지(회색)"를 구분하려는 의도였지만, **가장 심각한 상태가 화면에서 가장 약해 보이는** 역전이 생겼다. 다크에서는 `#cbd5e1`이 흰색처럼 보여 이상 지표 값이 정상 값보다도 흐렸다.

그 탓에 우회가 세 군데 쌓였고, 팔레트를 바로잡으면서 **전부 걷어냈다**.

| 걷어낸 우회 | 내용 |
|---|---|
| 조치 배너 | FAULT만 배경을 채워 강조 → 모든 배너가 같은 형태, 심각도는 색이 말한다 |
| 요약 타일 | FAULT 톤을 일부러 제외 → 고장이 있으면 FAULT색을 그대로 쓴다 |
| 이상 지표 값 | `METRIC_ALERT_COLORS`로 텍스트 색만 분리 → 상수 삭제, 상태색을 그대로 쓴다 |

**"노랑" 대신 앰버를 쓰는 이유 (실측).** 흰 배경에서 순수 노랑(`#eab308`)은 대비 **1.92:1**로 WCAG 텍스트 기준(4.5:1)에 한참 못 미친다. 읽히는 노랑(`#a16207`, 4.92:1)은 올리브·갈색으로 보여 노랑 구실을 못 한다. 앰버 `#d97706`을 유지하고 DANGER를 주황으로 밀었다.

**남은 접근성 한계.** 인접 단계끼리의 밝기 대비가 1.1~1.5:1이라 **색상(hue)으로만 구분된다.** 종전 FAULT 슬레이트는 밝기로도 구분됐지만(14.6:1) 램프에서는 그 성질이 사라진다. 적록색약 사용자를 위해 배지에는 상태 텍스트(`DANGER`, `FAULT`)를 항상 함께 표시한다 — 색만으로 판단하게 두지 않는다.
