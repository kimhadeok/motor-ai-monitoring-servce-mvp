# 02. 시스템 아키텍처 명세

> 원본: `.claude/docs/user/전체 시스템 아키텍처 흐름도.md`, `.claude/docs/user/모터 AI 니터링 시스템 아키텍처.md`, `.claude/docs/user/AI 에이전트 아키텍처 상세 설계.md`
> 작성: coreagent · 상태: 확정

## 1. 핵심 흐름 (요약)

```
현장 모터 센서 ➔ 데이터 수집/저장 ➔ 상태 분류·필터링 ➔ (전이 발생 시) 이벤트 발행
   ➔ 담당자 알림 발송 ➔ AI 에이전트 가동(컨텍스트+RAG 결합 진단) ➔ 진단 결과 합성
   ➔ 리포트 생성 + 대시보드 UI 갱신
```

## 2. 계층별 구조

### 2.1 현장 및 데이터 수집 계층

- 대상 지표: 온도, 진동, 전류, 소음
- 수집 주기: 10초 / 20초 / 30초 (모터별 설정)
- API를 통해 수신 → DB 저장 (보관 범위: 48시간)
- 프론트엔드 실시간 대시보드로 동시 렌더링
- 백그라운드 프로세스: 데이터 미수신 여부, 중단된 작업(예: PDF 생성 중 정지) 체크

### 2.2 컨텍스트 및 상태 분석 계층

- 수집 데이터를 4단계 상태(NORMAL/WARNING/DANGER/FAULT)로 분류 (지표별 개별 판정: 온도/진동/전류/소음 각각)
- 컨텍스트 매니저가 모터별 정보 집약
  - 단기 버퍼: 최근 2시간 데이터 윈도우 (실시간 진단용)
  - 장기 트렌드: 최근 6시간 데이터 (돌발 vs 점진적 악화 판정용)
  - RAG 지식베이스: Vector DB(ChromaDB)에서 제조사 매뉴얼 및 과거 유사 장애 이력 검색
- 슬라이딩 윈도우 방식으로 경량 관리 (거대 영구 DB 스캔 대신 최근 구간만 유지)
- **RAG 폴백 (2026-08-04 확정)**: 임베딩이 OpenAI API 기반(`01_tech_stack.md` §2.4)이므로 네트워크 의존이 있다. API 키 부재·호출 실패·타임아웃 시 예외를 삼켜 앱이 죽지 않도록 하고, SOP 조회는 원본 텍스트에 대한 **키워드 매칭으로 폴백**한다. RAG 없이도 앱은 정상 기동한다.
- **결정적 지식 조회 (2026-08-07 확정)**: 벡터 검색 이전에 참조 지식(`01_tech_stack.md` §2.3.1)에서 해당 지표의 의심 고장모드를 **결정적으로** 조회한다. 이 결과는 두 곳에 쓰인다. ① 리포트의 "의심 고장 모드" 섹션에 근거·부품·출처와 함께 노출 ② 벡터 검색 질의문 보강. 질의문이 `"{모터명} {지표} 이상 대응 정비 절차"` 뿐이면 도메인 어휘가 없어 유사도가 느슨하게 퍼지므로, 고장모드 이름을 넣어 검색을 좁힌다. 질의 보강에는 relevance 2(보조)까지만 쓴다 — 3(참고)까지 넣으면 전류 조회에 "축 정렬 불량"이 섞여 전기적 고장 절차를 밀어낸다. 지식 조회는 파일 읽기라 API 키 없이도 동작한다.
- **SOP 문서 유형 필터 (2026-08-07 확정)**: 벡터 검색과 키워드 폴백 모두 `doc_type ∈ (manual, incident)`로 제한한다. 방법론 문서(`methodology`)가 "이상 대응 정비 절차" 질의에 걸리면 실행 불가능한 설명 문장이 SOP로 나간다. 폴백은 여기에 더해 `manual`을 `incident`보다 먼저 소진해, 사례 서술이 실제 절차 자리를 차지하지 않게 한다.

### 2.3 상태 전이 및 이벤트 제어 계층

- **핑퐁 방지 원칙**: 수치의 잦은 흔들림을 막기 위해 절대값이 아닌 **상태 전이(Transition)** 시점 기준으로만 이벤트 처리

**핑퐁 방지 구현 (2026-08-05 확정)** — 전이 시점 기준만으로는 부족하다. 값이 임계선 위에서 미세하게 흔들리면 전이 자체가 반복 성립하기 때문이다. 두 장치를 함께 적용한다.

| 장치             | 값                                   | 규칙                                                                                                                                                                                                                                                                                 |
| ---------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 확정 시간        | `TRANSITION_CONFIRM_SECONDS = 300` | 새 상태가**5분간 연속 유지**될 때만 전이로 확정한다. 샘플 "개수"가 아니라 "시간" 기준인 이유는 수집 주기가 모터마다 10/20/30초로 달라, 개수 기준이면 확정까지 걸리는 시간이 모터마다 3배씩 차이 나기 때문이다. 필요한 연속 샘플 수는 `ceil(확정시간 / 수집주기)`로 환산한다. |
| 이력폭(deadband) | `TRANSITION_DEADBAND_RATIO = 0.05` | 상위 상태로**올라갈 때는 임계값을 그대로** 쓰고, **내려올 때만 진입 임계보다 5% 더 낮아지기**를 요구한다. 예: 진동 WARNING(임계 2.5)에서 NORMAL로 회복하려면 2.375 이하로 내려가야 한다.                                                                                 |

이력폭이 없으면 느린 램프 구간에서 왕복 전이가 대량 발생한다. 실제로 진동이 12시간에 걸쳐 2.1→3.7로 오를 때 노이즈 폭(±0.05)을 통과하는 데만 약 45분이 걸리고, 그동안 임계선을 계속 넘나들어 1~3분 간격 전이가 쏟아졌다. 두 장치 적용 후 전체 전이가 25건 → 9건으로 줄고 30분 내 왕복 전이는 0건, 최소 전이 간격은 196분이 되었다.

담당자 관점에서 이것은 **경보 피로(alarm fatigue)** 문제다. 몇 분 간격으로 상태가 오르내리는 화면은 "센서가 고장 났거나 시스템을 못 믿겠다"는 인상을 주고, 알림까지 그렇게 오면 사용자는 알림을 꺼버린다.

- 상태별 대응:| 전이              | 처리                                                                            |
  | ----------------- | ------------------------------------------------------------------------------- |
  | NORMAL → WARNING | 조용히 이벤트 로그만 적재 (전조 증상 분석용 컨텍스트로 활용)                    |
  | WARNING → DANGER | 쿨다운 통과 시 **담당자 알림 즉시 발송** → AI 에이전트 가동, 윈도우 데이터 + RAG 매뉴얼로 진단 후 리포트 HTML 생성·저장 |
  | FAULT             | DANGER와 동일하게 쿨다운 통과 시 알림 발송 → AI 에이전트 가동 → 리포트 HTML 생성·저장 (자동 처리, `03_state_event_logic.md` §4.1/§7 확정) |
- **알림이 진단·리포트보다 먼저다** (2026-08-13 사용자 확정 — 종전 순서를 뒤집음). 문자·알림톡은 게이트웨이 왕복 지연이 있고, 알림 문구가 진단 결과에 의존하지 않으며, 진단·리포트가 실측 4.12초(프로세스 첫 건 5~9초, §2.4.1)를 잡아먹는다. 근거 전문은 `03_state_event_logic.md` §4.1.
- **쿨다운 타임**: 전이 종류 무관(`03_state_event_logic.md` §5 확정) 1시간 동안 중복 개입 차단 (알람 폭탄/서버 부하 방지). 판정은 알림 발송 앞에서 하며, 막히면 알림과 에이전트 가동이 함께 차단된다
- 조건 충족 시 내부 메시지 큐에 이벤트 **1건만** 발행

### 2.4 AI 에이전트 가동 및 도구 실행 계층

- LLM 코어 엔진이 실시간 수치 + 컨텍스트 + RAG 매뉴얼을 종합 분석
- 실행 도구(Tool):| 도구                | 역할                                               |
  | ------------------- | -------------------------------------------------- |
  | 시계열 패턴 분석 툴 | 특정 주파수·진동 급증 등 이상 패턴 수치 검증      |
  | 장애 원인 추론 툴   | 현상별 고장 원인 역추적                            |
  | 대응 매뉴얼 조회 툴 | 정비 가이드 및 표준 조치 사항 매칭 (RAG 결과 기반) |
- 구현 기술: LangChain(툴 정의/실행), LangGraph(에이전트 실행 흐름) — `01_tech_stack.md` 참고

#### 2.4.1 진단 에이전트 구현 (2026-08-10)

`app/agents/diagnosis_agent.py` — LangGraph 최소 그래프 **`prepare` → `diagnose` → `finalize`**.

| 노드         | 하는 일                                                                                                                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prepare`  | 이미 측정된 근거를 프롬프트 메시지로 조립한다.**DB·지식 조회를 하지 않는다** — 호출측이 리포트 렌더에 쓰려고 가져온 값을 그대로 넘겨받아, 리포트 본문과 진단 프롬프트가 다른 근거를 보는 상황을 막는다 |
| `diagnose` | GPT-4o`with_structured_output(DiagnosisPayload)` 호출. 실패를 예외가 아니라 `fallback_reason`으로 표현한다                                                                                                 |
| `finalize` | 검증·폴백 게이트. 통과한 것만`source="llm"`이 된다                                                                                                                                                          |

**입출력 구조체는 템플릿과 분리한다** (`app/agents/schema.py`). `DiagnosisResult`(요약/원인/연쇄 영향/방치 시 결과 + `source`)는 리포트뿐 아니라 이후 별도 진단 화면도 그대로 소비한다. LLM에 요구하는 스키마는 `DiagnosisPayload`(4개 필드)로 따로 두는데, `source`까지 넣으면 모델이 생성 주체를 스스로 채워 폴백 결과에 `"llm"`이 실릴 수 있기 때문이다 — 그 값으로 리포트의 진단 모델 라벨을 고른다.

**`finalize`가 수치 인용을 실제로 검사한다.** 측정 근거를 프롬프트로 넣어줘도 GPT-4o가 "온도가 급격히 상승하여 냉각 문제로 보입니다" 같은 일반론을 반환하는 것을 실측했다. 어느 모터에나 들어맞는 문장은 담당자가 근거로 삼을 수 없고, `06_report_spec.md` §2.3이 규칙 기반 템플릿에서 걷어낸 문제를 되살린다. 요약·원인에 등장하는 숫자를 정규식으로 뽑아 실제 측정값(현재값·임계값·추세 시작/끝/최고·동반 지표값)과 오차 0.05 이내로 대조하고, 하나도 맞지 않으면 규칙 기반으로 교체한다. 반올림 표기(92.4 vs 92.43)를 허용하는 폭이다.

**폴백은 항상 규칙 기반 진단이다** (`services/diagnosis.build_rule_based_result`). 키 부재·`DIAGNOSIS_LLM_ENABLED=false`·타임아웃·API 오류·검증 실패·그래프 실행 실패를 모두 흡수하며, `run_diagnosis()`는 어떤 경우에도 예외를 던지지 않는다. 폴백으로 생성한 리포트는 진단 모델 라벨이 `"규칙 기반 진단 (LLM 미사용)"`으로 바뀐다 — 호출하지 않은 모델명을 적으면 담당자가 LLM 생성물로 오독한다.

**실측 (2026-08-10, 로컬)**

| 경로                                   | 소요             | 비고                                                             |
| -------------------------------------- | ---------------- | ---------------------------------------------------------------- |
| 리포트 최초 열람 (프로세스 첫 회)      | **5~9초**  | 3회 측정 5.29 / 6.03 / 8.53초. langgraph 콜드 import 3.17초 포함 |
| 리포트 최초 생성 (2건째, import 웜)    | **4.12초** | 진단 LLM 3.7초 + SOP 임베딩 0.3초                                |
| 재열람 (`report_html` 캐시)          | **0.03초** | LLM·RAG 호출 없음                                               |
| 폴백 (`DIAGNOSIS_LLM_ENABLED=false`) | 2.52초           | SOP 벡터 검색만                                                  |
| 폴백 (키 없음)                         | 0.37초           | SOP도 키워드 폴백                                                |
| 앱 진입 경로 import                    | 1.33초           | langgraph 미로드 확인                                            |

**첫 열람 시간이 5~9초로 흔들리는 이유는 GPT-4o 응답 지연 자체다.** 나머지 구성요소(콜드 import 3.17초, SOP 임베딩 0.3초, Jinja2 렌더 1ms 미만)는 회차 간 편차가 작다. 타임아웃·재시도는 `DIAGNOSIS_LLM_TIMEOUT_SECONDS`(12초) × `DIAGNOSIS_LLM_MAX_RETRIES`(1)로 묶여 있어, 최악의 경우 약 24초 뒤 규칙 기반으로 떨어진다.

### 2.5 진단 결과 합성 및 출력 계층

- 진단 결과 합성기(Synthesizer)가 원인 분석 및 대응 조치를 리포트로 생성 (`06_report_spec.md` 연계)
  - **리포트 HTML은 최초 열람 시 생성**해 `motor_status_logs.report_html`에 저장한다 (2026-08-07 변경 — 종전 "진단 시점 전건 생성"은 RAG 임베딩 왕복이 콜드 스타트를 지배해 폐기. §6.1.1). Jinja2 렌더 자체는 순수 Python이라 항상 성공한다
  - 이 경로에 **진단 에이전트 호출이 들어 있다** (2026-08-10, §2.4.1) — 첫 열람 5~9초, 이후 캐시로 0.03초
  - **PDF는 사용자가 리포트를 요청하는 시점에 생성**해 `report_pdf` BLOB에 캐시한다 (2026-08-04 확정, `06_report_spec.md` §1)
- 대시보드 UI: 모터 상태 컬러 코딩 갱신
- 관리자 알림: 채널별 발송 이력 적재 (`04_database_schema.md`의 `notification_logs` — KAKAO_ALIMTALK/SMS/EMAIL)
  - **발송은 이 계층을 기다리지 않는다** (2026-08-13). 알림은 §2.3 이벤트 발행 직후 나가고, 이 절의 진단·리포트는 그 뒤에 이어진다. 여기 적힌 "적재"는 리포트가 §5에서 그 이력을 읽어 표시하는 쪽을 말한다(`06 §2.5`)
  - **MVP는 적재까지다 (2026-08-10 확정).** 실제 채널 발송 어댑터는 정식 서비스 개발 시 적용한다 — 채널 계약·발신번호 등록·실패 재시도 같은 운영 요소가 붙고, 시연으로 보여줄 대상도 아니다. MVP는 시연용 샘플 이력을 시드가 만든다(`04 §3.7`).

## 3. 메시지 중계 방식 (보강 — MVP 적용 방식 제안)

원본 문서들은 상태 전이 이벤트 중계 수단으로 **RabbitMQ 또는 Redis Pub/Sub**를 명시함. 그러나 이는 별도 브로커 인프라 구축이 필요하며, `01_tech_stack.md`에 확정된 MVP 스택(Streamlit + SQLite 중심의 단일 프로세스 구조)에는 명시되어 있지 않아 스택 간 공백이 있음.

**MVP 제안**: 별도 메시지 브로커 없이, 아래 중 하나로 단순화

1. 상태 전이 감지 → 즉시 함수 호출(인메모리)로 AI 에이전트 트리거 (동일 프로세스 내 처리, 가장 단순)
2. 경량 백그라운드 스케줄러(APScheduler 등)가 주기적으로 DB의 상태 전이 여부를 폴링 후 트리거

정식 서비스 확장 시 RabbitMQ/Redis Pub/Sub로 전환 가능하도록 트리거 로직은 별도 함수/모듈로 분리 구현 권장. → 최종 방식은 `03_state_event_logic.md`에서 확정.

## 6. 데모 데이터 부트스트랩 (2026-08-04 확정)

배포 환경인 Streamlit Community Cloud는 재배포/재시작 시 로컬 파일시스템이 초기화된다(`01_tech_stack.md` §2.6). MVP 시연에 필요한 데이터(SQLite, ChromaDB persist 디렉터리, 리포트 HTML)를 어떻게 확보할지에 대한 확정 방식은 다음과 같다.

### 6.1 방식: 시간 의존 데이터만 부팅 시 런타임 생성

**가르는 기준은 "실행 시점"이 아니라 "데이터가 시간에 의존하는가"다 (2026-08-07 확정).**

데모 텔레메트리는 `app/services/seeding.py`가 `datetime.now(timezone.utc)` 기준으로 최근 48시간을 채운다. 커밋하면 배포 며칠 뒤 그 구간이 비어 **로그인 시 빈 대시보드**를 보게 되므로 부팅마다 새로 만든다. 반대로 RAG 벡터와 참조 지식은 시간에 무관하므로 커밋하고 부팅에서 뺐다.

| 자산                       | 시간 의존 | 저장                              | 생성 시점                               |
| -------------------------- | --------- | --------------------------------- | --------------------------------------- |
| 텔레메트리·상태로그·알림 | O         | `data/app.db` (gitignore)       | 부팅                                    |
| RAG 벡터                   | X         | `data/chroma/` (커밋)           | `scripts/build_knowledge.py` 수동 1회 |
| 참조 지식                  | X         | `data/knowledge/*.json` (커밋)  | 없음 — 파일이 곧 데이터                |
| 리포트 HTML                | O         | `motor_status_logs.report_html` | 최초 열람 시 (§6.1.1)                  |

```
ensure_demo_data()
  1. 스키마 보장 (CREATE TABLE IF NOT EXISTS)
  2. 데이터가 이미 있고 신선하면 시드 skip (재실행 안전)
  3. 데모 데이터 시드 — 회사/담당자/모터/임계값/텔레메트리/상태전이 로그/알림
  4. RAG 적재 확인 — collection.count()만 읽는다 (인제스트 아님)
```

**신선도 판정 (2026-08-07 추가).** 2단계는 모터 존재 여부만 보면 안 된다. 시드는 **실행 시각 기준** 최근 48시간을 채우므로, 앱을 오래 켜두거나 다음 날 다시 열면 최근 구간이 비어 **모터 그래프·카드 스파크라인(3시간 창)과 모터 세부정보(6시간 창)가 "데이터 없음"** 이 된다. 실제로 시드 6.6시간 뒤 그래프가 전부 비는 것을 확인했다.

`_demo_data_is_fresh()`가 최신 텔레메트리 나이를 함께 본다. `config.DEMO_DATA_MAX_AGE_HOURS`(2시간)를 넘으면 **DB를 지우고 다시 만든다** — 남겨두고 덧붙이면 옛 텔레메트리와 상태 로그가 섞여 "최근 48시간"이 두 구간으로 갈라진다. 임계는 그래프 창(6시간)보다 넉넉히 작게 잡아 창이 비기 전에 갱신되게 했다.

배포 환경은 파일시스템이 초기화돼 매번 새로 시드하므로 이 문제가 없지만, 로컬 개발과 장시간 시연에서는 반드시 발생한다.

**저장 밀도: 걷기와 저장을 분리한다 (2026-08-11 추가).** 배포본 콜드 부팅이 23.28초였고 그중 시드가 21.74초였다(`remaining_work` #12). 원인은 모터 대수가 아니라 **짧은 수집 주기**다 — 288,210행 중 커레이션 20대(10/20/30초)가 178,580행(62%)을 만들었다.

그런데 그 촘촘함은 **오래된 구간에서는 화면에 보이지 않는다.** 화면이 보는 창은 길어야 최근 6시간이다 — 모터 그래프 페이지 **3시간**(`GRAPH_TREND_HOURS`), 모터 세부정보 **6시간**(`DETAIL_TREND_HOURS`), 카드 스파크라인 **3시간**(`TREND_WINDOW_HOURS`). 그리고 **세 곳 모두 2026-08-12부터 그 창을 원본 그대로 그린다**(05 §3-A·§3.2·§4.1-A) — 구간 평균이 스파이크를 지웠기 때문이고, 카드 스파크라인도 같은 원칙으로 맞췄다. 다운샘플(15분 버킷 평균) 경로는 되돌릴 수 있게 함수와 상수를 남겨 두었을 뿐 호출부가 없다. **그래프의 원본 표시는 아래 표의 "최근 8시간 전량 저장"에 의존한다** — 그 밖은 15분 간격으로만 저장돼 있어, 창을 그보다 넓히면 그만큼 성겨진다. 그래서 `_generate_series()`는 **48시간을 원래 수집 주기 그대로 걷되**(이력폭 판정과 확정 샘플 수가 그 촘촘함에 의존한다 — 걸음을 성기게 하면 전이 이력 자체가 달라진다) **저장은 세 가지만** 한다.

| 저장 대상                                                  | 근거                                                                                                                                                                                                              |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 최근`SEED_DENSE_WINDOW_HOURS`(8h) 안의 모든 행           | 화면이 보는 창(6h)보다 넉넉히                                                                                                                                                                                     |
| **전이 확정 시각의 행과 그 직전 행**                 | 이벤트 목록의 "값 변화"가`time = created_at`으로 정확히 조인하고 직전 행을 서브쿼리로 가져온다(`services/events.py`). 리포트도 같은 시각의 행이 없으면 **아예 생성되지 않는다**(`reports/service.py`) |
| 그 밖의 구간은`SEED_SPARSE_INTERVAL_SECONDS`(900초) 간격 | 오래된 구간의 밀도를 전 모터 동일하게                                                                                                                                                                             |

**예외 하나 — FAULT 벌크 모터는 짧은 주기로 수집한다** (2026-08-11). 대시보드 카드는 심각도 순이라 FAULT 모터가 첫 줄을 차지하는데, 그들이 300초면 자동 갱신이 돌아도 첫 줄이 5분간 멈춰 있다. `SEED_BULK_FAULT_INTERVAL_SECONDS`(10초)를 주어 시연에서 실시간을 한자리에서 보여줄 수 있게 했다(05 §5-2-2). 조밀 창 안에서만 촘촘해지므로 비용은 4대 기준 약 1.1만 행이다.

실측: **288,210행 3.80초 → 92,997행 2.62초**(-68% 행, -31% 시간), 전이 80건·통보 이벤트 24건·모터 210대 불변(발송 기록은 2026-08-12부터 채널당 한 행이라 48행이다, `04 §3.7`). 부트스트랩 전체는 4.43초 → 3.29초. (FAULT 4대를 10초로 돌리기 전에는 81,858행 1.95초였다 — 그 차이가 첫 줄을 살리는 값이다.) 시드 시간은 생성 1.67초 / INSERT 2.06초 / commit 0.07초로 나뉘므로 **생성 1.70초가 이 방식의 하한**이다.

**배포 환경 실측 (2026-08-12)**: 콜드 부팅 **23.28초 → 7.27초**(schema 0.28 · seed **5.71** · rag_check 1.29). 시드가 21.74초 → 5.71초로 **3.8배** 줄었다 — 로컬 감소폭(-49%)보다 훨씬 큰데, 원래 배포 시드가 로컬의 5배 이상 느렸기 때문이다. `rag_ready=True rag_chunks=44`도 함께 확인됐다.

**결과: 부팅 경로에 OpenAI API 호출이 하나도 없다.** 배포본이 API 키 없이도 정상 기동하며, 키는 리포트 열람 시점에만 쓰인다.

### 6.1.2 런타임 틱 — 시드 이후의 데이터 (2026-08-11 추가)

시드는 **실행 시각까지만** 채운다. 그래서 자동 갱신(05 §5-2)만 붙이면 화면은 10초마다 다시 그려지지만 보이는 숫자는 그대로여서, 담당자 눈에는 아무 일도 일어나지 않는다.

`app/services/runtime_tick.py`의 `run_tick()`이 갱신 주기마다 **모터별 마지막 저장 시각 이후 경과분**을 이어 붙인다. 자동 갱신을 적용한 두 화면(메인 대시보드·모터 상세)에서만 호출한다. 실측 12초에 7행 · 8~45ms.

조절 값 (`config.py`):

| 상수                                 | 값       | 뜻                                                                                                                                                               |
| ------------------------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RUNTIME_TICK_ENABLED`             | `True` | 틱 전체 스위치. 끄면 시드된 구간만 보이고 화면이 멈춘다                                                                                                          |
| `RUNTIME_TICK_MAX_STEPS_PER_MOTOR` | 60       | 한 번의 틱에서 한 모터가 채울 최대 샘플 수                                                                                                                       |
| `RUNTIME_TICK_NOISE_RATIO`         | 0.05     | 한 걸음의 흔들림 폭 — 해당 상태 구간 폭에 대한 비율. 지표마다 구간 폭이 크게 달라(온도 WARNING 15.0 vs 진동 1.5) 절대값으로 주면 한쪽은 안 움직이고 한쪽은 튄다 |
| `RUNTIME_TICK_BAND_MARGIN_RATIO`   | 0.02     | 구간 경계에서 남길 여유 — 반올림으로 경계를 넘어 상태가 바뀌는 것을 막는다                                                                                      |
| `RUNTIME_TICK_FAULT_HEADROOM`      | 1.15     | FAULT 구간은 상한이 없으므로 고장 임계의 이 배수까지만 허용한다                                                                                                  |

**틱은 상태를 바꾸지 않고 상태 로그도 남기지 않는다.** 실시간 전이 판정(2-1)은 MVP 범위 밖으로 확정됐는데(2026-08-11), 값만 자유롭게 흔들면 임계를 넘는 순간 카드 색이 바뀌면서 이벤트 목록에는 아무 기록이 없는 어긋난 화면이 된다 — 대표 상태는 최신 텔레메트리 행의 지표별 상태에서 나오기 때문이다. 그래서 값은 **마지막 행이 속한 상태 구간 안에서만** 흔들린다(`_status_band()`가 `classify()`의 역함수). 실측으로 확인: 틱 3회 후 상태가 바뀐 모터 0대, 상태로그 80건 유지.

**다중 탭**: Streamlit은 세션마다 스크립트를 실행하므로 탭이 둘이면 틱도 둘이다. 난수를 `(motor_id, timestamp)`로 시드해 같은 시각에 같은 값이 나오게 하고, `INSERT OR IGNORE`(PK `(time, motor_id)`)로 중복을 흡수한다.

**밀린 구간**: 앱을 오래 띄워두고 돌아오면 `RUNTIME_TICK_MAX_STEPS_PER_MOTOR`(60)까지만 채우고 앞은 비운다. 전부 채우느라 화면이 멈추는 것을 막기 위함이며, 빈 구간이 있어도 그래프는 그려진다 — 원본을 시간축에 그대로 얹으므로 그 구간만 선이 길게 이어진다.

**신선도 판정과의 관계**: 틱이 최신 텔레메트리를 계속 밀어 올리므로, 앱을 켜둔 채로는 `DEMO_DATA_MAX_AGE_HOURS`(2h) 재시드가 걸리지 않는다. 재시드는 앱을 2시간 이상 꺼두었다가 다시 열 때 일어난다.

4단계는 인제스트가 아니라 진단용 확인이다. 벡터 스토어가 비어 있으면 `rag_ready=False`로 알려 SOP 조회가 키워드 폴백으로 동작 중임을 드러낸다 — 커밋된 `data/chroma/`가 배포에 제대로 실렸는지 확인하는 장치다. 실측 0.87초가 드는데 이는 Chroma 클라이언트를 여는 비용이고, 클라이언트가 모듈 전역이라 첫 리포트 열람 때 재사용된다(2회차 0.01초). 총합은 같고 첫 리포트가 그만큼 빨라진다.

### 6.1.1 리포트 HTML 생성 시점 (2026-08-07 변경)

**진단 시 전건 생성 → 최초 열람 시 생성**으로 바꿨다. Jinja2 렌더 자체는 건당 1ms 미만이지만, `build_report_context()`가 호출하는 `query_sop_steps()`가 건당 임베딩 API 왕복을 유발한다. **실측 24건 8.80초(건당 0.37초)로 콜드 스타트를 지배했다.**

지연 생성 경로는 `app/reports/service.py:get_report()`에 이미 있었다(`report_html`이 NULL이면 그 자리에서 만들어 저장). UI 어디에도 `report_html IS NOT NULL` 조건이 없어 부팅 호출만 제거하면 됐다. 로컬에서 전건을 미리 만들려면 `scripts/seed_data.py --with-reports`를 쓴다.

**이 결정이 2026-08-10에 값을 다시 했다.** 진단 에이전트(§2.4.1)가 붙으면서 건당 비용이 0.37초 → 약 4초(임베딩 0.3초 + GPT-4o 3.7초)로 올랐다. 전건 생성을 유지했다면 콜드 부팅에 **24회 LLM 호출·약 90초**가 걸렸을 것이다. 지금도 부팅 경로의 OpenAI 호출은 0회이며, `--with-reports`는 시작 전 건수와 예상 소요를 출력한다. 템플릿이나 진단 로직을 바꾼 뒤 저장된 HTML을 비우려면 `scripts/seed_data.py --reset-reports`를 쓴다.

**RAG 인제스트 생략 조건 (2026-08-05 확정, 수동 스크립트에 계속 적용).** 컬렉션의 `count()`가 원본 청크 수와 일치하면 재임베딩하지 않는다. 청크 수가 그대로인 채 원본 내용만 바뀐 경우는 감지하지 못하며, 이때는 `scripts/build_knowledge.py --force`를 쓴다. `--force`는 `data/chroma/`를 통째로 비우고 다시 만든다 — Chroma의 `delete_collection()`이 세그먼트 디렉터리를 디스크에 남겨서, 재빌드마다 `data_level0.bin`(약 0.6MB)이 쌓이고 산출물을 커밋하므로 git 히스토리에 영구 누적되기 때문이다(실측 6회 재빌드 후 4.4MB → 정리 후 1.3MB).

**시드 규모 (2026-08-06 갱신)**: 회사 2곳, **COMP-001 200대 + COMP-002 10대 = 총 210대**. 200대는 모터 그래프(§05 §3-A)의 세로 스크롤·페이지네이션과 모터 현황(§05 §3-B)의 그룹핑·10열 배치 밀도를 시연에서 보여주기 위한 규모다(회사 격리로 COMP-002 계정은 10대만 본다). COMP-001의 벌크 190대는 수집주기 300초로 생성해 텔레메트리 행 수를 억제한다.

**2026-08-11 재측정** (모터 210대, 텔레메트리 **92,997행**, DANGER/FAULT 24건, RAG 44청크)

> 2026-08-07 측정치는 텔레메트리 288,210행 기준 시드 3.93초 · 합계 4.43초였다. §6.1의 저장 밀도 조정으로 행이 줄어 시드가 빨라졌고, FAULT 모터 4대에 짧은 수집 주기를 준 만큼(05 §5-2-2) 일부 되돌아온 값이다.

즉 같은 규모에서 종전 방식이었다면 약 14.6초였을 콜드 스타트가 **3.29초**가 됐다. 배포 환경은 파일시스템이 초기화되므로 항상 콜드 경로를 탄다.

리포트 HTML 생성 시간은 Jinja2 렌더(건당 1ms 미만)가 아니라 그 안에서 호출하는 RAG SOP 조회(건당 0.37초의 임베딩 API 왕복)가 지배한다. 이 비용은 사라진 게 아니라 열람 시점으로 옮겨간 것이므로, 사용자는 리포트를 처음 열 때 약 0.4초를 기다린다(2회차부터는 저장된 HTML을 그대로 쓴다).

대시보드(§05 §3.1~3.3) 렌더는 COMP-001 로그인 시 **모터 카드 200개**를 그린다 — 카드가 인라인 SVG·게이지·흐름 애니메이션을 담아 무거우므로 렌더 부담이 있다(성능 개선 검토는 `remaining_work.md #7`). 전체 목록 조망은 모터 현황(§05 §3-B) 페이지가 경량 카드로 담당한다.

PDF는 이 단계에 포함하지 않는다. 건당 약 0.5초로 전건 생성 시 약 8초가 추가되는데, 네이티브 라이브러리가 없는 개발 환경에서는 그 시간이 전량 실패로 낭비되기 때문이다.

### 6.2 선택 근거

- 시드 산출물을 커밋하는 방식은 **데이터 노후화 문제**가 있다. 텔레메트리는 생성 시점 기준 상대 시간으로 만들어지는데, 단기 버퍼(2h)·장기 트렌드(6h)·보관 범위(48h)는 모두 "현재" 기준이므로 커밋 후 시간이 지나면 최근 구간이 빈다. 런타임 생성은 항상 "지금 기준 최근 48시간"이 되어 이 문제가 발생하지 않는다.
- 바이너리 산출물(SQLite DB, 벡터 인덱스)을 저장소에서 제외해 이력을 깨끗하게 유지한다.
- 리포트가 배포 환경에서 생성되므로 폰트·레이아웃이 실제 서비스와 일치한다.

### 6.3 동시성 및 폴백

- `@st.cache_resource`로 프로세스당 1회 실행을 보장하고, 파일 락(`data/.ingest.lock`)과 완료 마커(`data/.ingest_done`)로 동시 진입을 차단한다. 시드가 기존 DB를 삭제 후 재생성하는 경로가 있으므로, 한 세션이 삭제하는 동안 다른 세션이 읽는 상황을 반드시 막아야 한다. 락을 얻지 못한 세션은 스키마만 확인하고 즉시 반환한다.
- OpenAI API 키 부재나 호출 실패 시 **RAG 없이 기동**한다 (§2.2 폴백).
- **부트스트랩 전체가 실패해도 앱은 기동한다 (2026-08-05 확정).** 시드·인제스트·리포트 생성 중 예외가 나면 삼켜서 반환값에 `error`로 담고, 진입점이 경고 배너만 띄운 뒤 화면을 그린다. 데이터 준비 실패로 앱이 크래시하지 않도록 하기 위해서다. 완료 마커를 만들지 않으므로 다음 기동에서 다시 시도한다.

### 6.4 수동 실행 스크립트

두 스크립트의 역할이 다르다.

| 스크립트                                                              | 대상                  | 실행 빈도                                                                |
| --------------------------------------------------------------------- | --------------------- | ------------------------------------------------------------------------ |
| `scripts/seed_data.py [--force] [--with-reports] [--reset-reports]` | 시간 의존 데모 데이터 | 로컬 재생성용 (선택). 평상시엔 부팅이 처리한다                           |
| `scripts/build_knowledge.py [--force] [--dry-run]`                  | RAG 벡터 스토어       | **원본 텍스트를 수정했을 때만.** 산출물을 커밋해야 배포에 반영된다 |

`--dry-run`은 임베딩 없이 청크 수·doc_type 분포·파일별 내역만 출력하므로 API 키 없이도 구성을 확인할 수 있다. `--reset-reports`(2026-08-10 추가)는 저장된 `report_html`/`report_pdf`를 비워 다음 열람에서 다시 생성되게 한다 — 템플릿이나 진단 로직을 바꿔도 이미 저장된 HTML은 갱신되지 않기 때문이다(`06_report_spec.md` §3). 두 스크립트 모두 부트스트랩과 동일한 `app/` 로직을 호출하며 별도 구현을 두지 않는다.

**`build_knowledge.py`는 앱을 내린 상태에서 실행한다 (2026-08-07 검증 중 확인).** Chroma의 persist 디렉터리는 다중 프로세스 동시 쓰기를 가정하지 않는다. 앱이 클라이언트를 연 채로 스토어가 갱신되면 앱 쪽 벡터 검색이 **예외 없이 조용히 실패**해 SOP가 키워드 폴백으로 떨어진다 — 검증 중 실제로 재현했고, 앱을 재기동하자 정상 복귀했다. 폴백이 예외를 삼키는 설계(§2.2)라 로그에도 남지 않으므로, SOP가 갑자기 옛 매뉴얼 문구로 돌아갔다면 이 상황을 먼저 의심한다. 배포 환경은 Streamlit 프로세스 하나만 스토어를 읽으므로 해당하지 않는다.

### 6.5 관측 — 부팅 요약 로그 (2026-08-10 추가)

**배포 환경에서 앱 내부 상태를 볼 통로는 Manage app 로그(프로세스 stdout/stderr)뿐이다.** 화면에 드러나지 않는 실패가 셋 있는데, 그중 둘은 사용자도 관리자도 알아챌 방법이 없었다.

| 실패                          | 사용자에게 보이는가                             | 판정 방법                        |
| ----------------------------- | ----------------------------------------------- | -------------------------------- |
| RAG 미적재 → SOP 키워드 폴백 | **안 보인다** (문구가 그럴듯해 구분 불가) | 부팅 로그`rag_ready` + WARNING |
| 진단 LLM 실패 → 규칙 기반    | 리포트의 "진단 모델" 라벨로 보인다 (§2.4.1)    | 진단 로그`source=` + 폴백 사유 |
| PDF 변환 불가 → HTML 제공    | 보인다 (HTML로 표시됨)                          | —                               |

`app/logging_setup.py`의 `configure_logging()`이 `app.*` 네임스페이스에 stderr 핸들러를 1회 붙인다. 진입점(`main.py`, `scripts/seed_data.py`)에서 호출한다.

**왜 별도 설정이 필요한가.** 핸들러가 없는 로거의 INFO는 버려지고 WARNING 이상만 `lastResort`로 나간다. Streamlit이 붙이는 핸들러는 `streamlit` 네임스페이스 전용이라 앱 로그에 걸리지 않는다. `propagate = False`로 루트에 올리지 않아 중복 출력도 막는다. 레벨은 `LOG_LEVEL`(기본 `INFO`)로 조절하며, 알 수 없는 값이 들어와도 INFO로 떨어지고 앱은 죽지 않는다.

**남기는 것 (실측 출력)**

```
INFO  [app.services.bootstrap] 환경 | python=3.14.6 streamlit=1.60.0 chromadb=1.5.9 langgraph=1.2.10 | openai_key=설정됨 diagnosis_llm=on
INFO  [app.services.bootstrap] 부트스트랩 완료 | 모터 210대 텔레메트리 92,997행 상태로그 80건 | reseeded_stale=False | rag_ready=True rag_chunks=44 | 3.29s (schema=0.08s seed=2.62s rag_check=0.59s)
WARN  [app.services.bootstrap] RAG 벡터가 비어 있음 | SOP 조회가 키워드 폴백으로 동작합니다. …
INFO  [app.agents.diagnosis_agent] 진단 생성 | MTR-227 sound | source=llm | 6.31s
INFO  [app.agents.diagnosis_agent] 진단 생성 | MTR-227 sound | source=rule (DIAGNOSIS_LLM_ENABLED=false) | 0.34s
```

환경 줄 하나로 배포 검증 항목 다수가 정리된다 — 선택된 Python 버전, `chromadb`가 커밋된 persist 포맷과 같은 버전인지, 키가 Secrets에 들어갔는지. **API 키 값 자체는 절대 남기지 않는다.** 설정 여부만 찍는다.

**배포본 실측 (2026-08-10)** — Streamlit Community Cloud, `motor-049` 반영본:

```
환경 | python=3.14.7 streamlit=1.60.0 chromadb=1.5.9 langgraph=1.2.10 | openai_key=설정됨 diagnosis_llm=off
부트스트랩 완료 | 모터 210대 텔레메트리 288,210행 상태로그 80건 | rag_ready=True rag_chunks=44
  | 23.28s (schema=0.10s seed=21.74s rag_check=1.45s)
```

**Python 3.14가 그대로 선택된다** — `requires-python = ">=3.14"`를 낮출 필요가 없었다. 커밋한 `data/chroma/`도 정상 로드돼(`rag_ready=True`) SOP가 실제 벡터 검색으로 동작한다.

**콜드 부팅은 로컬 4.49초 대비 23.28초로 약 5배**였다. 차이는 거의 전부 시드(3.94초 → 21.74초)이며 배포 환경의 CPU·디스크가 느린 탓이다. 앱이 잠들었다 깨거나 데모 데이터가 낡아 재시드될 때 **첫 방문자가 그만큼 기다린다** — `remaining_work #12`에서 다룬다.

**배포본 재실측 (2026-08-12)** — 시드 축소(`#12`) 반영 후, `diagnosis_llm`을 `on`으로 바꾼 뒤:

```
환경 | python=3.14.7 streamlit=1.60.0 chromadb=1.5.9 langgraph=1.2.10 | openai_key=설정됨 diagnosis_llm=on
부트스트랩 완료 | 모터 210대 텔레메트리 92,997행 상태로그 80건 | reseeded_stale=False
  | rag_ready=True rag_chunks=44 | 7.27s (schema=0.28s seed=5.71s rag_check=1.29s)
```

**23.28초 → 7.27초**(시드 21.74 → 5.71초, 3.8배). 위 §6.1의 저장량 축소가 배포 환경에서 로컬보다 큰 폭으로 나타났다 — 원래 배포 시드가 로컬의 5배 이상 느렸기 때문이다. `openai_key=설정됨 diagnosis_llm=on`으로 **LLM 경로가 켜져 있는 것도 확인**됐고, 배포본에서 리포트를 열어 **`source=llm`도 확인 완료**다(2026-08-12, `remaining_work` #5). 즉 배포본의 "AI 진단"은 실제 GPT-4o 생성물이다.

**배포본도 진단 LLM을 켠다 (2026-08-11 결정 — 2026-08-10 방침을 뒤집음).** Secrets에 `DIAGNOSIS_LLM_ENABLED = "true"`를 둔다(항목을 빼도 기본값이 `true`). 구매 검토 고객에게 보여줄 배포본에서 "AI 진단"이 실제로는 규칙 기반인 것이 시연상 가장 큰 약점이라는 판단이다.

종전 방침은 공개 URL + 시연 계정 노출(`05_ui_screens.md` §2)로 GPT-4o 호출을 통제할 수 없다는 우려였다. 호출 구조를 다시 확인한 결과 **노출 규모가 유계**임이 확인돼 방침을 바꿨다.

| 항목                    | 값                           | 근거                                                                                                                  |
| ----------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 호출 시점               | [보고서] 클릭당 최초 1회     | 부팅 경로에 LLM 호출 없음.`generate_missing_report_html()`은 `scripts/seed_data.py --with-reports`에서만 호출된다 |
| 재열람                  | 호출 없음                    | `report_html`이 있으면 진단을 건너뛴다 (`reports/service.get_report_assets`)                                      |
| 부팅 1회당 상한         | **24호출**             | 리포트 대상 = DANGER 19 + FAULT 5                                                                                     |
| 상한이 다시 열리는 조건 | 재시드 (재부팅·데이터 노후) | 캐시가 DB에 있으므로 재시드 시 초기화된다                                                                             |
| 소요                    | LLM 6.31초 vs 규칙 0.34초    | 로컬 실측                                                                                                             |

`true`여도 타임아웃·API 오류·출력 검증 실패는 규칙 기반으로 폴백하며 라벨이 바뀐다 — 실제 경로는 로그의 `source=llm` / `source=rule`로 판정한다. **배포 환경에서 LLM 경로가 실제로 도는 것은 미검증이다**(배포본은 계속 `off`였다). 재배포 후 로그로 확인한다.

**단, `OPENAI_API_KEY`는 Secrets에 유지한다.** 이 스위치는 진단 LLM만 끈다. 키를 비우면 `get_collection()`이 임베딩 함수 없이 열리지 않아 `rag_ready=False`가 되고 SOP까지 키워드 폴백으로 떨어진다(실측 확인). 임베딩 비용은 질의당 $0.00002 수준이라 통제 대상이 아니다.

**로그 스트림은 UTF-8로 강제한다.** 배포 대상(Linux)은 UTF-8이라 무관하지만, Windows 콘솔은 기본 코드페이지가 cp949라 한글 로그가 깨져 로컬에서 읽을 수 없었다. `_log_stream()`이 인코딩이 UTF-8이 아닐 때만 `TextIOWrapper`로 감싼다(래퍼가 GC되면 버퍼까지 닫히므로 모듈 레벨에서 참조를 붙든다).

### 6.6 PDF 검증 — 배포 환경과 같은 조건으로 로컬에서 (2026-08-10 추가)

**리포트 레이아웃은 브라우저로 검증할 수 없다.** WeasyPrint의 flexbox 구현이 Chromium과 달라, 브라우저에서 멀쩡한 문서가 PDF에서는 단어 중간에서 줄이 깨지고 페이지가 밀린다(`06_report_spec.md` §3.1의 차이 표). 실제로 첫 배포에서 6페이지 PDF와 잘린 머리글이 나왔고, 배포→확인→수정을 반복할 뻔했다.

Windows에는 WeasyPrint의 네이티브 라이브러리(Pango 등)가 없어 로컬 생성이 불가능하다. **배포 환경과 같은 Debian trixie 컨테이너를 쓴다.**

**이미지 이름은 `motor-weasy:trixie`로 고정한다** (2026-08-11 추가). 이미지가 1.99GB라 이름을 정해두지 않으면 검증할 때마다 같은 내용의 이미지가 새로 쌓인다 — 실제로 이름이 문서에 없어 두 번째 이미지가 만들어졌다. 빌드 전에 `docker images | grep motor-weasy`로 존재를 먼저 확인한다.

```bash
docker build -t motor-weasy:trixie .
```

```dockerfile
FROM python:3.14-trixie
RUN apt-get update && apt-get install -y --no-install-recommends \
        libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0 fonts-noto-cjk \
    && rm -rf /var/lib/apt/lists/*
RUN pip install --no-cache-dir weasyprint==69.0 pymupdf
```

apt 목록은 저장소의 `packages.txt`와 같게 유지한다 — 이 컨테이너가 배포 환경의 대역이 되려면 두 목록이 어긋나면 안 된다.

절차: 앱에서 리포트 HTML을 파일로 뽑는다 → 컨테이너에서 `HTML(filename=...).write_pdf(...)` → `pymupdf`로 페이지 수·페이지별 내용 하단 y좌표·머리글 문자열이 조각났는지 확인. 페이지 이미지를 PNG로 뽑으면 눈으로도 확인할 수 있다.

**PDF를 읽기만 할 때는 컨테이너도 필요 없다.** `uv run --with pymupdf` 한 줄이면 PDF를 PNG로 변환해 확인할 수 있다(poppler 설치 불필요). 배포본에서 내려받은 PDF를 점검할 때 쓴다.

검증할 것: ① 페이지 수가 5장인가 ② 각 페이지 내용이 본문 774pt 안에 들어오는가 ③ 머리글·배지 문자열이 한 줄로 유지되는가.
