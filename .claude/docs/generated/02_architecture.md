# 02. 시스템 아키텍처 명세

> 원본: `.claude/docs/user/전체 시스템 아키텍처 흐름도.md`, `.claude/docs/user/모터 AI 니터링 시스템 아키텍처.md`, `.claude/docs/user/AI 에이전트 아키텍처 상세 설계.md`
> 작성: coreagent · 상태: 확정

## 1. 핵심 흐름 (요약)

```
현장 모터 센서 ➔ 데이터 수집/저장 ➔ 상태 분류·필터링 ➔ (전이 발생 시) 이벤트 발행
   ➔ AI 에이전트 가동(컨텍스트+RAG 결합 진단) ➔ 진단 결과 합성 ➔ 알림 + 대시보드 UI 갱신
```

## 2. 계층별 구조

### 2.1 현장 및 데이터 수집 계층

- 대상 지표: 온도, 진동, 전류, 소음
- 수집 주기: 10초 / 20초 / 30초 (모터별 설정)
- API를 통해 수신 → DB 저장 (보관 범위: 48시간)
- 프론트엔드 실시간 대시보드로 동시 렌더링
- 백그라운드 프로세스: 데이터 미수신 여부, 중단된 작업(예: PDF 생성 중 정지) 체크

### 2.2 컨텍스트 및 상태 분석 계층

- 수집 데이터를 4단계 상태(NORMAL/WARNING/DANGER/FAULT)로 분류 (지표별 개별 판정: 온도/진동/전류/소음 각각)
- 컨텍스트 매니저가 모터별 정보 집약
  - 단기 버퍼: 최근 2시간 데이터 윈도우 (실시간 진단용)
  - 장기 트렌드: 최근 6시간 데이터 (돌발 vs 점진적 악화 판정용)
  - RAG 지식베이스: Vector DB(ChromaDB)에서 제조사 매뉴얼 및 과거 유사 장애 이력 검색
- 슬라이딩 윈도우 방식으로 경량 관리 (거대 영구 DB 스캔 대신 최근 구간만 유지)
- **RAG 폴백 (2026-08-04 확정)**: 임베딩이 OpenAI API 기반(`01_tech_stack.md` §2.4)이므로 네트워크 의존이 있다. API 키 부재·호출 실패·타임아웃 시 예외를 삼켜 앱이 죽지 않도록 하고, SOP 조회는 원본 텍스트에 대한 **키워드 매칭으로 폴백**한다. RAG 없이도 앱은 정상 기동한다.

### 2.3 상태 전이 및 이벤트 제어 계층

- **핑퐁 방지 원칙**: 수치의 잦은 흔들림을 막기 위해 절대값이 아닌 **상태 전이(Transition)** 시점 기준으로만 이벤트 처리
- 상태별 대응:| 전이              | 처리                                                                            |
  | ----------------- | ------------------------------------------------------------------------------- |
  | NORMAL → WARNING | 조용히 이벤트 로그만 적재 (전조 증상 분석용 컨텍스트로 활용)                    |
  | WARNING → DANGER | 쿨다운 통과 시 AI 에이전트 즉시 가동, 윈도우 데이터 + RAG 매뉴얼로 진단 후 리포트 HTML 생성·저장 → 알림 |
  | FAULT             | DANGER와 동일하게 쿨다운 통과 시 AI 에이전트 즉시 가동 → 리포트 HTML 생성·저장 → 알림 발송 (자동 처리, `03_state_event_logic.md` §4.1/§7 확정) |
- **쿨다운 타임**: 전이 종류 무관(`03_state_event_logic.md` §5 확정) 1시간 동안 중복 개입 차단 (알람 폭탄/서버 부하 방지)
- 조건 충족 시 내부 메시지 큐에 이벤트 **1건만** 발행

### 2.4 AI 에이전트 가동 및 도구 실행 계층

- LLM 코어 엔진이 실시간 수치 + 컨텍스트 + RAG 매뉴얼을 종합 분석
- 실행 도구(Tool):| 도구                | 역할                                               |
  | ------------------- | -------------------------------------------------- |
  | 시계열 패턴 분석 툴 | 특정 주파수·진동 급증 등 이상 패턴 수치 검증      |
  | 장애 원인 추론 툴   | 현상별 고장 원인 역추적                            |
  | 대응 매뉴얼 조회 툴 | 정비 가이드 및 표준 조치 사항 매칭 (RAG 결과 기반) |
- 구현 기술: LangChain(툴 정의/실행), LangGraph(에이전트 실행 흐름) — `01_tech_stack.md` 참고

### 2.5 진단 결과 합성 및 출력 계층

- 진단 결과 합성기(Synthesizer)가 원인 분석 및 대응 조치를 리포트로 생성 (`06_report_spec.md` 연계)
  - 진단 시점에는 **리포트 HTML을 생성해 `motor_status_logs.report_html`에 저장**한다 (Jinja2 렌더는 순수 Python이라 항상 성공)
  - **PDF는 사용자가 리포트를 요청하는 시점에 생성**해 `report_pdf` BLOB에 캐시한다 (2026-08-04 확정, `06_report_spec.md` §1)
- 대시보드 UI: 모터 상태 컬러 코딩 갱신
- 관리자 알림: 채널별 발송 (`04_database_schema.md`의 `notification_logs` — KAKAO_ALIMTALK/SMS/EMAIL)

## 3. 메시지 중계 방식 (보강 — MVP 적용 방식 제안)

원본 문서들은 상태 전이 이벤트 중계 수단으로 **RabbitMQ 또는 Redis Pub/Sub**를 명시함. 그러나 이는 별도 브로커 인프라 구축이 필요하며, `01_tech_stack.md`에 확정된 MVP 스택(Streamlit + SQLite 중심의 단일 프로세스 구조)에는 명시되어 있지 않아 스택 간 공백이 있음.

**MVP 제안**: 별도 메시지 브로커 없이, 아래 중 하나로 단순화

1. 상태 전이 감지 → 즉시 함수 호출(인메모리)로 AI 에이전트 트리거 (동일 프로세스 내 처리, 가장 단순)
2. 경량 백그라운드 스케줄러(APScheduler 등)가 주기적으로 DB의 상태 전이 여부를 폴링 후 트리거

정식 서비스 확장 시 RabbitMQ/Redis Pub/Sub로 전환 가능하도록 트리거 로직은 별도 함수/모듈로 분리 구현 권장. → 최종 방식은 `03_state_event_logic.md`에서 확정.

## 6. 데모 데이터 부트스트랩 (2026-08-04 확정)

배포 환경인 Streamlit Community Cloud는 재배포/재시작 시 로컬 파일시스템이 초기화된다(`01_tech_stack.md` §2.6). MVP 시연에 필요한 데이터(SQLite, ChromaDB persist 디렉터리, 리포트 HTML)를 어떻게 확보할지에 대한 확정 방식은 다음과 같다.

### 6.1 방식: 앱 부팅 시 런타임 생성

산출물을 git에 커밋하지 않고, **앱이 부팅될 때 실행 환경에서 직접 생성**한다.

```
ensure_demo_data()
  1. 스키마 보장 (CREATE TABLE IF NOT EXISTS)
  2. 데이터가 이미 있으면 시드 skip (재실행 안전)
  3. 데모 데이터 시드 — 회사/담당자/모터/임계값/텔레메트리/상태전이 로그/알림
  4. RAG 인제스트 — data/rag_sources/*.txt → ChromaDB (OpenAI 임베딩)
       적재된 청크 수가 원본 청크 수와 같으면 생략 (아래 참조)
  5. DANGER/FAULT 로그 전건에 대해 리포트 HTML 생성·저장
```

**RAG 인제스트 생략 조건 (2026-08-05 확정).** 컬렉션의 `count()`가 원본 청크 수와 일치하면 재임베딩하지 않는다. 부팅마다 컬렉션을 지우고 다시 만들면 OpenAI 임베딩 API를 반복 호출하게 되고, 삭제·재생성 왕복 자체가 콜드 스타트에 수 초를 더한다. `count()`는 임베딩을 요구하지 않으므로 판정 비용은 없다. 청크 수가 그대로인 채 원본 내용만 바뀐 경우는 감지하지 못하며, 이때는 `scripts/seed_data.py --force`로 재인제스트한다(§6.4).

| 단계 | 콜드 (첫 기동) | 웜 (재기동) |
|---|---|---|
| 스키마 | 0.07초 | 0.00초 |
| 시드 (텔레메트리 63,366행) | 0.68초 | 생략 |
| RAG 인제스트 (11청크, OpenAI 임베딩) | 1.39초 | 0.48초 (생략 판정만) |
| 리포트 HTML 전건 생성 (4건) | 1.25초 | 0.00초 |
| **합계** | **약 3.4초** | **약 0.5초** |

배포 환경은 파일시스템이 초기화되므로 항상 콜드 경로를 탄다. 리포트 HTML 생성 시간은 Jinja2 렌더(건당 1ms 미만)가 아니라 그 안에서 호출하는 RAG SOP 조회(건당 약 0.3초의 임베딩 API 왕복)가 지배한다.

PDF는 이 단계에 포함하지 않는다. 건당 약 0.5초로 전건 생성 시 약 8초가 추가되는데, 네이티브 라이브러리가 없는 개발 환경에서는 그 시간이 전량 실패로 낭비되기 때문이다.

### 6.2 선택 근거

- 시드 산출물을 커밋하는 방식은 **데이터 노후화 문제**가 있다. 텔레메트리는 생성 시점 기준 상대 시간으로 만들어지는데, 단기 버퍼(2h)·장기 트렌드(6h)·보관 범위(48h)는 모두 "현재" 기준이므로 커밋 후 시간이 지나면 최근 구간이 빈다. 런타임 생성은 항상 "지금 기준 최근 48시간"이 되어 이 문제가 발생하지 않는다.
- 바이너리 산출물(SQLite DB, 벡터 인덱스)을 저장소에서 제외해 이력을 깨끗하게 유지한다.
- 리포트가 배포 환경에서 생성되므로 폰트·레이아웃이 실제 서비스와 일치한다.

### 6.3 동시성 및 폴백

- `@st.cache_resource`로 프로세스당 1회 실행을 보장하고, 파일 락(`data/.ingest.lock`)과 완료 마커(`data/.ingest_done`)로 동시 진입을 차단한다. 시드가 기존 DB를 삭제 후 재생성하는 경로가 있으므로, 한 세션이 삭제하는 동안 다른 세션이 읽는 상황을 반드시 막아야 한다. 락을 얻지 못한 세션은 스키마만 확인하고 즉시 반환한다.
- OpenAI API 키 부재나 호출 실패 시 **RAG 없이 기동**한다 (§2.2 폴백).
- **부트스트랩 전체가 실패해도 앱은 기동한다 (2026-08-05 확정).** 시드·인제스트·리포트 생성 중 예외가 나면 삼켜서 반환값에 `error`로 담고, 진입점이 경고 배너만 띄운 뒤 화면을 그린다. 데이터 준비 실패로 앱이 크래시하지 않도록 하기 위해서다. 완료 마커를 만들지 않으므로 다음 기동에서 다시 시도한다.

### 6.4 수동 재생성

`scripts/seed_data.py`는 로컬에서 데모 데이터를 다시 만들고 싶을 때 쓰는 선택적 CLI 진입점으로 유지한다. 부트스트랩과 동일한 `app/` 로직을 호출하며, 별도 구현을 두지 않는다.
