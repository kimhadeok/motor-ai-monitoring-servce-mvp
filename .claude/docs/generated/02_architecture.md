# 02. 시스템 아키텍처 명세

> 원본: `.claude/docs/user/전체 시스템 아키텍처 흐름도.md`, `.claude/docs/user/모터 AI 니터링 시스템 아키텍처.md`, `.claude/docs/user/AI 에이전트 아키텍처 상세 설계.md`
> 작성: coreagent · 상태: 확정

## 1. 핵심 흐름 (요약)

```
현장 모터 센서 ➔ 데이터 수집/저장 ➔ 상태 분류·필터링 ➔ (전이 발생 시) 이벤트 발행
   ➔ AI 에이전트 가동(컨텍스트+RAG 결합 진단) ➔ 진단 결과 합성 ➔ 알림 + 대시보드 UI 갱신
```

## 2. 계층별 구조

### 2.1 현장 및 데이터 수집 계층

- 대상 지표: 온도, 진동, 전류, 소음
- 수집 주기: 10초 / 20초 / 30초 (모터별 설정)
- API를 통해 수신 → DB 저장 (보관 범위: 48시간)
- 프론트엔드 실시간 대시보드로 동시 렌더링
- 백그라운드 프로세스: 데이터 미수신 여부, 중단된 작업(예: PDF 생성 중 정지) 체크

### 2.2 컨텍스트 및 상태 분석 계층

- 수집 데이터를 4단계 상태(NORMAL/WARNING/DANGER/FAULT)로 분류 (지표별 개별 판정: 온도/진동/전류/소음 각각)
- 컨텍스트 매니저가 모터별 정보 집약
  - 단기 버퍼: 최근 2시간 데이터 윈도우 (실시간 진단용)
  - 장기 트렌드: 최근 6시간 데이터 (돌발 vs 점진적 악화 판정용)
  - RAG 지식베이스: Vector DB(ChromaDB)에서 제조사 매뉴얼 및 과거 유사 장애 이력 검색
- 슬라이딩 윈도우 방식으로 경량 관리 (거대 영구 DB 스캔 대신 최근 구간만 유지)

### 2.3 상태 전이 및 이벤트 제어 계층

- **핑퐁 방지 원칙**: 수치의 잦은 흔들림을 막기 위해 절대값이 아닌 **상태 전이(Transition)** 시점 기준으로만 이벤트 처리
- 상태별 대응:| 전이              | 처리                                                                            |
  | ----------------- | ------------------------------------------------------------------------------- |
  | NORMAL → WARNING | 조용히 이벤트 로그만 적재 (전조 증상 분석용 컨텍스트로 활용)                    |
  | WARNING → DANGER | 쿨다운 통과 시 AI 에이전트 즉시 가동, 윈도우 데이터 + RAG 매뉴얼로 진단 후 알림 |
  | FAULT             | 이미 정지 상태 — 사후 분석용 리포트 대기 모드                                  |
- **쿨다운 타임**: 전이 발생(NORMAL→WARNING, WARNING→DANGER 공통) 후 1시간 동안 중복 개입 차단 (알람 폭탄/서버 부하 방지)
- 조건 충족 시 내부 메시지 큐에 이벤트 **1건만** 발행

### 2.4 AI 에이전트 가동 및 도구 실행 계층

- LLM 코어 엔진이 실시간 수치 + 컨텍스트 + RAG 매뉴얼을 종합 분석
- 실행 도구(Tool):| 도구                | 역할                                               |
  | ------------------- | -------------------------------------------------- |
  | 시계열 패턴 분석 툴 | 특정 주파수·진동 급증 등 이상 패턴 수치 검증      |
  | 장애 원인 추론 툴   | 현상별 고장 원인 역추적                            |
  | 대응 매뉴얼 조회 툴 | 정비 가이드 및 표준 조치 사항 매칭 (RAG 결과 기반) |
- 구현 기술: LangChain(툴 정의/실행), LangGraph(에이전트 실행 흐름) — `01_tech_stack.md` 참고

### 2.5 진단 결과 합성 및 출력 계층

- 진단 결과 합성기(Synthesizer)가 원인 분석 및 대응 조치를 리포트로 생성 (`06_report_spec.md` 연계)
- 대시보드 UI: 모터 상태 컬러 코딩 갱신
- 관리자 알림: 채널별 발송 (`04_database_schema.md`의 `notification_logs` — KAKAO_ALIMTALK/SMS/EMAIL)

## 3. 메시지 중계 방식 (보강 — MVP 적용 방식 제안)

원본 문서들은 상태 전이 이벤트 중계 수단으로 **RabbitMQ 또는 Redis Pub/Sub**를 명시함. 그러나 이는 별도 브로커 인프라 구축이 필요하며, `01_tech_stack.md`에 확정된 MVP 스택(Streamlit + SQLite 중심의 단일 프로세스 구조)에는 명시되어 있지 않아 스택 간 공백이 있음.

**MVP 제안**: 별도 메시지 브로커 없이, 아래 중 하나로 단순화

1. 상태 전이 감지 → 즉시 함수 호출(인메모리)로 AI 에이전트 트리거 (동일 프로세스 내 처리, 가장 단순)
2. 경량 백그라운드 스케줄러(APScheduler 등)가 주기적으로 DB의 상태 전이 여부를 폴링 후 트리거

정식 서비스 확장 시 RabbitMQ/Redis Pub/Sub로 전환 가능하도록 트리거 로직은 별도 함수/모듈로 분리 구현 권장. → 최종 방식은 `03_state_event_logic.md`에서 확정.

## 5. 핵심 파라미터 확정값

원본 3개 문서에서 아래 수치가 문서마다 다르게 기재되어 있었으나(단기 버퍼 1시간/2시간, 쿨다운 전이별 차등 등), 사용자 확인을 거쳐 아래 값으로 확정했습니다. 상세 상태 전이 규칙은 `03_state_event_logic.md`에서 이 값을 기준으로 구체화합니다.

| 항목 | 확정값 |
| --- | --- |
| 단기 버퍼 (실시간 진단) | 2시간 |

| 쿨다운 — NORMAL → WARNING | 1시간 |
| 쿨다운 — WARNING → DANGER | 1시간 |
