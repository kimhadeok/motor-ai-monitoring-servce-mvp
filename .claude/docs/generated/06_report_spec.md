# 06. 리포트(PDF) 생성 명세

> 원본: `.claude/docs/user/report_template.html`
> 반영: `01_tech_stack.md`(Jinja2/WeasyPrint), `03_state_event_logic.md`(DANGER/FAULT 자동 리포트 생성), `04_database_schema.md`(테이블 구조)
> 작성: coreagent · 상태: 확정

## 1. 렌더링 파이프라인

파이프라인은 **진단 시점**과 **리포트 요청 시점**의 두 구간으로 나뉜다 (2026-08-04 확정).

**① 진단 시점 — HTML 생성 (항상 수행)**

```
DANGER/FAULT 이벤트 발생 (03_state_event_logic.md)
  → AI 에이전트 진단 결과(텍스트/수치) 생성
  → Jinja2로 report_template.html에 데이터 바인딩
  → 렌더된 HTML을 motor_status_logs.report_html(TEXT)에 저장
  → notification_logs로 담당자에게 알림 발송
```

**② 리포트 요청 시점 — PDF 생성 (요청 시 1회, 이후 캐시)**

```
사용자가 리포트 버튼 클릭 (05_ui_screens.md §3.3)
  → report_pdf에 캐시가 있으면 그대로 제공
  → 없으면 저장된 report_html을 WeasyPrint로 PDF 변환 시도
       성공 → PDF 바이너리를 report_pdf(BLOB)에 캐시 후 다운로드 제공
       실패 → 저장된 report_html을 화면에 표시 (폴백)
```

**분리 근거**: Jinja2 HTML 렌더는 순수 Python이라 어떤 환경에서도 성공하지만, WeasyPrint PDF 변환은 Pango 등 네이티브 라이브러리가 설치된 환경에서만 동작한다(`01_tech_stack.md` §2.1). 이벤트 처리 경로가 PDF 생성 가능 여부에 의존하면 네이티브 의존이 없는 개발 환경에서 리포트가 통째로 누락되므로, HTML 생성을 진단 경로에 두고 PDF를 요청 경로로 분리했다. 부팅 시 전건 PDF 생성을 하지 않는 이유이기도 하다 — 건당 약 0.5초로 전건 생성 시 부팅이 약 8초 늘어나는데, PDF 생성이 불가한 환경에서는 그 시간이 전량 실패로 낭비된다.

어느 경로든 **파일시스템에 저장하거나 조회하지 않는다** (메모리 내 처리 후 DB 기록).

## 2. 섹션별 명세 및 MVP 데이터 매핑

원본 `report_template.html`은 특정 장애 사례(베어링 외륜 손상)를 가정한 **목업 데이터**로 채워져 있음. 아래는 각 섹션을 실제 MVP 데이터 소스에 매핑한 것.

### 2.1 헤더 / 메타 정보

| 템플릿 항목 | MVP 데이터 소스 |
|---|---|
| 상태 배지 (CRITICAL 등) | 이벤트를 유발한 상태 (`DANGER` 또는 `FAULT`) |
| 대상 설비 ID / 설치 위치 | `motors.motor_id`, `motors.installation_location` |
| 모터 규격/모델 | `motors.model_name` |
| 정격 속도/전압 | **리포트에서 제외 (확정)** — `motors` 스키마 확장하지 않음 |
| 이벤트 감지 시각 | `motor_status_logs.created_at` (해당 전이 로그) |
| 에이전트 세션 ID | `motor_{motor_id}_{날짜}_{시각}` 형식으로 확정 (예: `motor_MTR-001_20260803_171000`) |

### 2.2 센서 측정 데이터 표 (원본 §1)

**센서 카드 아이콘은 지표마다 다르다 (2026-08-10).** 4장이 같은 온도계 아이콘이라 카드를 훑을 때 라벨을 읽어야만 지표를 구분할 수 있었다. 지금은 온도=온도계, 진동=파형, 전류=번개, 소음=스피커로 나눠, 담당자가 이상 카드를 아이콘으로 먼저 잡아낸다. 템플릿의 `metric_icon()` 매크로가 `sensor.metric`(라벨이 아니라 지표명 — 문구가 바뀌어도 아이콘은 유지된다)으로 고른다.

이 변경으로 **온도계는 "온도" 전용 기호가 됐으므로**, "센서 일반"을 뜻하던 플로우 노드 `센서 데이터 수집`은 계기판 아이콘으로 바꿨다. 같은 페이지에서 온도계가 두 가지 의미로 읽히면 안 된다. 섹션 1 제목은 **번개 아이콘**을 쓴다(2026-08-10 사용자 지정) — 전류 카드와 같은 기호이지만 제목은 카드와 층위가 달라 혼동 소지가 적고, 면으로 채워진 도형이라 작은 크기에서 선 아이콘보다 또렷하다.

**아이콘 크기는 틀을 건드리지 않고 키웠다 (2026-08-10).** 모두 크기가 고정된 박스 안에 들어 있으므로, 안쪽 SVG만 키우면 레이아웃과 페이지 분할이 영향을 받지 않는다 — 변경 전후 페이지별 내용 하단 좌표가 동일함을 실측 확인했다.

| 위치 | 박스 | SVG |
|---|---|---|
| 센서 카드 | 38×38 | 18 → **22** |
| 섹션 제목 (h2) | 30×30 | 16 → **19** |
| 플로우 노드 | 44×44 | 20 → **24** |
| 타임라인 점 | 22×22 | 12 → **14** |

박스가 없는 아이콘(표지 브랜드, 내용 페이지 머리글)은 키우지 않았다. 줄 높이가 늘어 표지 여유(54pt)와 페이지 분할에 영향을 주기 때문이다.

아이콘은 외부 리소스 없이 inline SVG로만 그린다(오프라인 PDF 변환에서도 깨지지 않아야 한다). WeasyPrint가 확실히 지원하는 기본 도형(`rect`/`circle`/`path`)과 stroke 속성만 쓰며, trixie 컨테이너에서 정상 렌더를 확인했다.

원본 목업은 5개 세부 항목(베어링 하우징 온도, 진동속도 RMS, 진동가속도 Peak, 3상 전류 불평형률, 음향 FFT Peak)을 예시로 보여주나, `motor_telemetry`(04)에는 **온도/진동/전류/소음 4개 원시 값만** 존재. **MVP 범위 축소 제안**: 4개 항목 표로 단순화.

| 측정 항목 | 현재 측정값 | 정상 기준 범위 | 상태 평가 |
|---|---|---|---|
| 온도 | `motor_telemetry.temperature` | `motor_thresholds`(temperature) | `temp_status` |
| 진동 | `motor_telemetry.vibration` | `motor_thresholds`(vibration) | `vib_status` |
| 전류 | `motor_telemetry.current` | `motor_thresholds`(current) | `current_status` |
| 소음 | `motor_telemetry.sound` | `motor_thresholds`(sound) | `sound_status` |

값은 이벤트 발생 시점(`motor_status_logs.created_at`)의 `motor_telemetry` 레코드 기준.

**정상 기준·임계값 표는 모두 그 모터의 `motor_thresholds`에서 온다 (2026-08-11 정정).** 종전에는 센서 카드의 "정상 기준"만 `config.METRIC_THRESHOLDS` 전역값을 읽고 임계값 표는 DB를 읽어, 관리자에서 임계값을 바꾸면 **같은 리포트 한 장 안에 "정상 기준 ≤ 60 °C"와 "정상 구간 < 50"이 함께 찍혔다**(실측). 지금은 한 곳(`services/motors.get_metric_thresholds()`)에서 가져와 둘 다 만든다.

### 2.3 AI 진단 및 근본 원인 분석 (원본 §2)

| 템플릿 항목 | MVP 데이터 소스 |
|---|---|
| 추론 엔진 분석 결과 (요약/주요 원인/연쇄 영향/방치 시 예상 결과) | **LangGraph 진단 에이전트**(`app/agents/diagnosis_agent.py`, `02_architecture.md` §2.4.1)의 구조화 출력. LLM 이용 불가·검증 실패 시 `app/services/diagnosis.py`의 규칙 기반 진단으로 폴백한다 |
| **측정 근거 (2026-08-07 추가)** | `build_diagnosis_facts()`가 텔레메트리에서 계산. 단기(2h)·장기(6h) 윈도우의 시작→끝 값·변화량·표본 수, 같은 시점에 함께 정상 범위를 벗어난 지표 목록 |
| **지표 특성 (2026-08-07 추가)** | 참조 지식의 `metric_characteristics`. 진동=핵심 지표, 온도·소음=보조 지표, 전류=긴급 대응 지표와 각각의 주의사항·출처 |

**근거 계산과 문장 생성을 분리한 이유 (2026-08-07).** 종전 `build_diagnosis_text()`는 추세와 연쇄 영향을 측정하지 않고 문자열에 박아 두었다. 그 결과 **지표와 무관하게 항상 같은 문장**이 나갔다 — 전류 이상 리포트에도 "온도와 진동이 함께 상승하는 패턴은 베어링 윤활 부족의 전형적 징후"가 실렸다. 실측 확인 결과 이 문장이 사실과 맞는 경우는 DANGER/FAULT 24건 중 1건뿐이었다. "단기 버퍼 기준 상승 추세가 관측되며", "과거 유사 장애 이력과 일치합니다"도 계산·조회 없이 단언한 문장이었다.

지금은 `build_diagnosis_facts(conn, ...)`가 근거를 먼저 측정하고, 그 dict가 진단 에이전트의 grounding이자 규칙 기반 폴백(`build_rule_based_result`)의 입력이 된다. **측정하지 못한 항목은 아예 서술하지 않는다** — 표본이 없어 추세를 계산하지 못한 구간은 "변화 없음"이 아니라 프롬프트에서 줄 자체를 만들지 않는다. 에이전트에도 같은 제약을 걸고, `finalize` 노드가 수치 인용 여부를 실제로 검사한다(`02 §2.4.1`).

**진단은 4개 섹션으로 구조화된다 (2026-08-10 확정).** 종전 단일 문단(`{{ diagnosis_text }}`)을 **요약 / 주요 원인 / 연쇄 영향 / 방치 시 예상 결과**로 나눠 렌더한다. 요약은 강조 박스 한 줄, 연쇄 영향은 목록이다. 담당자가 필요한 항목만 골라 읽을 수 있고, 이후 진단 화면이 같은 구조체(`DiagnosisResult`)를 그대로 소비할 수 있다. 연쇄 영향 항목 수는 `DIAGNOSIS_MAX_CHAINED_EFFECTS`(3)로 제한한다 — 3페이지 여유 451px을 넘기지 않기 위한 것이며, 초과분은 폴백 사유가 아니라 잘라낸다(정확한 진단을 통째로 버리는 것보다 낫다).

**진단 모델 라벨은 생성 경로를 따라간다 (2026-08-10 확정).** LLM 성공 시 `"GPT-4o 기반 진단 에이전트"`, 폴백 시 `"규칙 기반 진단 (LLM 미사용)"`. 호출하지 않은 모델명을 적으면 담당자가 폴백 결과를 LLM 생성물로 오독한다 — 위에서 걷어낸 "측정하지 않은 것을 단언하는" 문제와 같은 선상이다.

**첫 열람 대기 (실측 2026-08-10).** 프로세스 최초 리포트는 5~9초(3회 측정 5.29 / 6.03 / 8.53초, langgraph 콜드 import 3.17초 포함), 이후 4.12초, 재열람은 캐시로 0.03초. 편차는 GPT-4o 응답 지연 자체에서 온다. 무엇을 기다리는지 알 수 있도록 스피너 문구를 "AI 진단 리포트를 생성하는 중입니다… (최초 열람은 몇 초 걸립니다)"로 둔다. 상세 표는 `02 §2.4.1`.

추세 윈도우는 `motors.get_metric_trend()`를 쓰지 않는다 — 그 함수는 "지금" 기준이라 과거 이벤트 리포트에서는 이벤트 이후 수집분이 섞인다. `diagnosis._measure_trend()`가 윈도우를 이벤트 시각에서 끊는다. 변화율이 `TREND_SIGNIFICANT_RATIO`(3%) 미만이면 "유지"로 서술해, 센서 노이즈를 추세로 오독하지 않는다.

**"방치 시 예상 결과"는 여유 시간대에 연동된다.** 의심 고장 모드 중 가장 급한 `lead_time_band`를 골라 DAYS는 "이번 교대 내 조치", WEEKS는 "다음 계획 정비까지 미루지 마십시오", MONTHS는 "계획 정비 일정에 포함" 으로 서술한다.
| 진단 신뢰도(%) + 진행바 | **리포트에서 제외 (확정)** — LLM에 confidence 출력을 요구하는 추가 설계 없이 진단 텍스트만 표시 |
| 진단 모델명 표시 | **생성 경로에 따라 달라진다 (2026-08-10)**: LLM 성공 시 `DIAGNOSIS_MODEL_LABEL`("GPT-4o 기반 진단 에이전트", `01_tech_stack.md` 모델과 일치), 폴백 시 `DIAGNOSIS_FALLBACK_MODEL_LABEL`("규칙 기반 진단 (LLM 미사용)") |
| **의심 고장 모드 (2026-08-07 추가)** | 참조 지식(`01_tech_stack.md` §2.3.1)에서 해당 지표로 **결정적 조회**. 항목별로 고장명(한/영), 여유 시간대, 진단 근거, 연관 강도, 교체 대상 부품, 출처 문서·페이지를 표시한다. 지식이 없으면 섹션 자체가 사라진다 |

**정렬은 여유 시간대(급한 것) 우선 (2026-08-07 확정).** 담당자가 위에서부터 읽으므로 `수일 내 조치`가 `수주 내 점검`보다 반드시 위에 온다. 긴급도가 같으면 `relevance` 순.

이 정렬은 보조 연관(relevance 2)이면서 급한 고장이 주요 연관(1)이면서 여유 있는 고장보다 위에 올 수 있다 — 예: 온도 조회에서 `과열(DAYS, 주요) > 과부하(DAYS, 보조) > 윤활 부족(WEEKS, 주요)`. 순서로 이 차이를 표현하지 않고 **`relevance_label`("주요 연관 / 보조 연관 / 참고")을 항목마다 함께 노출해** 해결한다. 순서는 급한 순, 판단 근거는 라벨로 제공하는 방식이다.

**의심 고장 모드를 벡터 검색으로 하지 않은 이유.** 같은 지표라면 같은 근거가 나와야 담당자가 리포트를 신뢰한다. 벡터 검색은 질의문의 미세한 차이로 결과가 흔들리므로 이 부분은 매핑 조회로 고정하고, 벡터 검색은 서술형 정비 절차(§2.4)에만 쓴다. 조회 결과는 §2.4의 질의문 보강에도 재사용된다.

**여유 시간대 표기.** MotorSense 제품소개서 p4의 징후 시간 체인(진동 Months → 소음 Weeks → 열·연기 Days → 고장)을 고장모드별로 "수개월 여유 / 수주 내 점검 / 수일 내 조치"로 표시한다. 같은 DANGER라도 남은 대응 시간이 다르다는 점을 드러내기 위한 것이다.

|---|---|
| 정비 조치 절차 (SOP 리스트) | RAG 대응 매뉴얼 조회 툴 출력 (`02_architecture.md` §2.4, ChromaDB 검색 결과). 질의문은 §2.3의 의심 고장모드 이름으로 보강하고, `doc_type ∈ (manual, incident)`로 제한한다. **RAG 이용 불가 시**(API 키 부재·호출 실패·타임아웃) 원본 텍스트 키워드 매칭으로 폴백하며, 그마저 결과가 없으면 안전 기본 문구를 표시한다 — `02_architecture.md` §2.2 |
| 자재 창고 예비 부품 재고 현황 (CMMS 연동) | **MVP 범위 밖 — 제외 확정**. CMMS 연동 시스템이 `01_tech_stack.md`에 없음. 다만 교체 대상 부품명은 §2.3 의심 고장 모드에 표시된다 |

**SOP 조회는 매뉴얼을 사례보다 먼저 채운다 (2026-08-07 확정).** `doc_type`을 한 번에 조회하면 사례 문단이 1순위로 올라와 "베어링 하우징 온도가 3시간에 걸쳐 상승했습니다" 같은 **증상 서술이 SOP 1단계 자리를 차지한다**(실측 확인). `manual` → `incident` 순으로 순회하며 `RAG_MAX_SOP_STEPS`를 채운다. 벡터 검색과 키워드 폴백이 동일한 우선순위를 쓴다.

**모터명은 사례 조회에만 넣는다 (2026-08-07 확정).** 매뉴얼은 기종 단위로 쓰여 특정 설비명을 담지 않으므로 질의문에 모터명을 넣으면 순위만 흔들린다 — A/B 실측에서 같은 온도 질의가 모터명에 따라 온도 절차와 진동 절차 사이를 오갔다. 과거 장애 이력은 특정 설비를 지칭하므로 사례 조회에는 유지한다.

**RAG 원본 작성 규칙 (2026-08-07 확정).** SOP 리스트는 검색된 문단을 문장 단위로 잘라 만든다(`app/rag/ingest.py:_split_steps`). 따라서 `data/rag_sources/*.txt`의 **모든 문장이 그 자체로 실행 가능한 조치여야 한다.** "조치 순서는 다음과 같다" 같은 도입 문장이나 "○○ 대응 절차." 같은 제목 문장을 넣으면 그것이 SOP 단계로 출력되어 실제 조치를 밀어낸다 — 초기 작성본에서 4단계 중 2단계가 이런 껍데기 문장으로 채워지는 것을 검증 중 확인했다. 진단 근거는 첫 문장에 괄호로 붙이고(예: "과열(표면 또는 권선 온도가 정격 초과) 대응 — 부하를 즉시 10~20% 낮춥니다."), 나머지 문장은 조치만 담는다.

### 2.5 자동 대응 및 통보 이력 (원본 §4)

| 템플릿 항목 | MVP 데이터 소스 |
|---|---|
| 이상 감지 / AI 분석 완료 타임스탬프 | `motor_status_logs.created_at`(이상 감지) + 리포트 생성 완료 시각(**HTML 렌더 시점** — PDF는 요청 시 생성되므로 기준으로 삼지 않는다, 2026-08-04 확정) — 에이전트 시작/종료 시각 별도 기록은 생략 |
| 자동 인터락(PLC 정지 제어) | **MVP 범위 밖 — 제외 확정**. PLC 연동 시스템 없음 (`01_tech_stack.md`) |
| 긴급 알림 발송 + ERP/CMMS 자재 예약(WO 생성) | 알림 부분만 유지: `notification_logs` 발송 이력. ERP/CMMS 자재 예약은 **MVP 범위 밖 — 제외 확정** |
| 수신 담당자 / 발송 문구 / **발송 채널** | `notification_logs.contact_id`(→ `company_contacts.contact_name`), `.message_content`, `.channel_type` — 채널별 수신처는 `company_contacts.phone_number` / `.email` |

**구현 (2026-08-11).** 이 매핑은 명세돼 있었지만 코드가 따르지 않고 있었다 — 담당자를 `company_contacts`의 첫 행에서 가져오고 발송 문구를 `build_notification_message()`로 그때그때 다시 만들었다. 그래서 리포트의 "발송 문구"가 실제로 기록된 알림이 아니었고, 시드가 만든 3채널 샘플 24건이 어느 화면에도 나오지 않았다(`remaining_work` #11).

`_lookup_notification()`이 `notification_logs`를 **`(motor_id, created_at)`** 로 조회한다. 이 테이블에는 상태 로그를 가리키는 FK가 없지만, 알림이 전이 시각을 그대로 `created_at`에 넣고 발행되므로 이 쌍이 곧 키다(시드 전 건 매칭 실측).

**발송 채널을 새로 노출한다** — 카카오 알림톡 / 문자 / 이메일(`config.NOTIFICATION_CHANNEL_LABELS`). DB 값은 영문 상수라 그대로 보이면 담당자가 어느 경로로 받았는지 바로 읽지 못한다. `SMS`의 라벨은 **"문자"** 다(2026-08-12) — 현장에서 쓰는 말이다.

#### 채널은 여럿이고, 수신처를 함께 적는다 (2026-08-12 사용자 확정)

**문자가 기본 채널이고 이메일이 함께 나간다 — 이메일만 단독으로 발송되지 않는다.** 한 이벤트에 `notification_logs` 행이 여러 개이므로(`04 §3.7`) 조회가 `LIMIT 1`에서 **전 행 조회**로 바뀌었다. 종전에는 첫 행만 읽어 "이메일" 하나만 적었고, **실제로 문자를 받은 담당자가 리포트에서 그 사실을 확인할 수 없었다.**

| 위치 | 표기 |
|---|---|
| 타임라인 | `알림 발송 — 담당자에게 리포트 다운로드 안내 발송 (문자, 이메일)` |
| 수신 담당자 | `김철수` — 연락처는 아래 채널 줄에 채널별로 적는다. 두 곳에 같은 번호가 나오면 어느 것이 무엇인지 흐려진다 |
| 발송 채널 | `문자 (010-****-5678)　이메일 (dem****@example.com)` |

- **순서는 기록순이 아니라 `config.NOTIFICATION_CHANNEL_ORDER`(문자 → 이메일 → 카카오 알림톡)** 를 따른다. 기본 채널이 먼저 읽혀야 한다.
- **수신처는 마스킹한다.** 전화번호 `010-****-5678`(기존), 이메일 **`dem****@example.com`** — 앞 3자만 남긴다(`_mask_email`). 리포트는 사고 조사에 첨부되어 외부로 나갈 수 있으므로 담당자 연락처를 그대로 남기지 않는다. 본인은 자기 주소를 알아보고 제3자는 복원하지 못하는 수준이다.
- **표시만 바꾸지 않은 이유**: 기록은 이메일 1건인데 화면이 "문자도 보냈다"고 말하면 2026-08-11에 고친 결함(리포트가 실제 기록과 다름)이 되살아난다. 그래서 시드가 채널당 한 행을 남기도록 바꿨다.

**기록이 없으면 사실대로 적는다.** 쿨다운으로 억제된 이벤트는 표에 "발송 없음 — 쿨다운 (직전 동일 지표 알림 후 1시간 이내)", 타임라인은 "알림 미발송"으로 바뀐다. 종전에는 타임라인이 무조건 "알림 발송"을 찍어, 담당자가 "통보됐다"고 믿고 넘어가면 실제로는 아무도 모르는 상태가 될 수 있었다. (현재 시드에는 억제된 건이 0건이라 이 분기는 방어용이다 — DANGER/FAULT 로그 24건 = **통보 이벤트 24건**. 발송 기록은 채널당 한 행이라 48행이다, `04 §3.7`.)

**타임라인의 발송 시각은 리포트 생성 시각(이벤트+12초)을 쓰고 `notification_logs.created_at`은 쓰지 않는다.** 시드에서 알림의 `created_at`이 전이 시각과 같아, 그대로 표시하면 "알림 발송"이 "AI 진단 완료"보다 앞서는 어긋난 순서가 된다.

레이아웃 영향: 표에 발송 채널 한 줄이 늘어 5페이지 내용 하단이 601.2pt → **619.8pt**(본문 한계 774pt). trixie 컨테이너에서 FAULT·DANGER·미발송 세 건 모두 5페이지 유지를 확인했다(`02 §6.6`).

> **2026-08-12 변경분의 레이아웃은 미검증이다.** 발송 채널 줄이 `이메일` 한 마디에서 `문자 (010-****-5678)　이메일 (dem****@example.com)`로 길어졌다. 각 채널을 `white-space: nowrap` 인라인 블록으로 두어 한 줄에 들어가도록 했지만, **A4 폭에서 실제로 줄바꿈이 없는지, 5페이지가 유지되는지는 trixie 컨테이너로 재검증해야 한다.** 채널이 셋(카카오 포함)이 되면 여유가 더 줄어든다.
>
> 참고: 사용자가 2026-08-12 배포본에서 PDF 생성을 확인했으나, **그 빌드에는 이 2채널 변경이 들어 있지 않다.** 위 재검증과는 별개다.

## 3. MVP 리포트 섹션 구성 (최종 제안)

위 매핑을 반영해 MVP 리포트는 원본의 5개 섹션 중 **CMMS 부품 재고, PLC 자동 인터락, ERP 자재 예약**을 제외한 아래 구성으로 축소 제안:

1. 헤더/메타 정보
2. 센서 측정 데이터 (4개 지표) + **지표별 임계값 표**
3. AI 진단 — 신뢰도 게이지 제외. **요약 / 주요 원인 / 연쇄 영향 / 방치 시 예상 결과** 4섹션 + **측정 근거**
3-1. 근본 원인 분석 (별도 섹션) — **지표 특성** + **의심 고장 모드**
4. 정비 가이드(SOP) — RAG 매뉴얼 기반, 이용 불가 시 키워드 매칭 폴백 (부품 재고 제외)
5. 자동 대응 이력 — 이상감지/AI분석/알림발송만 (PLC 인터락 제외)

**생성 시점 (2026-08-07 변경).** 리포트 HTML은 진단 시점이 아니라 **최초 열람 시** 생성해 `motor_status_logs.report_html`에 저장한다. 전건 생성은 건당 0.37초의 RAG 임베딩 왕복을 유발해 콜드 스타트를 지배했다(실측 24건 8.80초) — `02_architecture.md` §6.1.1. 진단 에이전트가 붙은 2026-08-10 이후 건당 비용은 약 4초로 올랐고(임베딩 0.3초 + LLM 3.7초), 이 결정이 없었다면 콜드 부팅에 **24회 LLM 호출**이 걸렸을 것이다. `scripts/seed_data.py --with-reports`(수동 전건 생성)는 시작 전 건수와 예상 소요를 출력한다.

> 템플릿을 수정해도 **이미 저장된 `report_html`에는 반영되지 않는다.** 로컬에서 변경을 확인하려면 `UPDATE motor_status_logs SET report_html = NULL, report_pdf = NULL` 후 다시 열거나 `scripts/seed_data.py --force`로 재생성한다.

### 3.1 PDF 페이지 구성 — 섹션당 한 페이지 (2026-08-07 확정)

A4(`@page { size: A4; margin: 12mm }`) 기준 본문 영역은 **703 × 1031px**(527 × 774pt)이다. **섹션 단위로 페이지를 나눈다.**

**아래 수치는 2026-08-10에 실제 PDF에서 다시 쟀다** (Debian trixie 컨테이너 + WeasyPrint 69, 배포 환경과 동일 조건). 종전 표는 브라우저 실측이었고 폭 조건이 달라 실제와 어긋나 있었다 — 아래 "브라우저 실측이 PDF를 대신하지 못했던 이유" 참조. 값은 본문 텍스트 하단 기준이다.

| 페이지 | 섹션 | 내용 하단 | 여유 |
|---|---|---|---|
| 1 | 표지 | 754pt | **54pt** |
| 2 | 1. 실시간 센서 측정 데이터 + 지표별 임계값 | 592pt | 216pt |
| 3 | 2. AI 진단 | 522~540pt | 268~286pt |
| 4 | 3. 근본 원인 분석 | 503pt | 305pt |
| 5 | 4. 정비 가이드(SOP) + 5. 자동 대응 및 통보 이력 | 601pt | 207pt |

표지 여유가 54pt로 가장 빠듯하지만, 표지는 **내용이 고정**이라 모터가 바뀌어도 흔들리지 않는다. 높이가 변하는 페이지(3·5)는 200pt 이상 남는다.

**브라우저 실측이 PDF를 대신하지 못했던 이유 (2026-08-10).** `.page`에 `max-width: 900px`가 걸려 있어 브라우저에서는 약 770px 폭으로 렌더됐는데, WeasyPrint는 A4 본문 폭 703px로 레이아웃한다. 좁은 쪽에서만 줄바꿈이 늘어나므로 브라우저에서 잰 높이가 실제보다 작게 나왔다. `.page { width: 186mm }`로 고정해 두 환경의 폭을 같게 만들었다. 다이얼로그에 표시되는 HTML도 이 폭이라 PDF와 같은 모습이 된다.

**WeasyPrint와 Chromium의 차이로 실제 배포본에서 깨졌던 것 (2026-08-10).** 첫 배포 PDF는 6페이지로 나왔고 머리글이 단어 중간에서 잘렸다.

| 증상 | 원인 | 대응 |
|---|---|---|
| `모터 AI 모니터링 서비/스`, `AI 모터 이상 진단 리포/트` 등 단어 중간 줄바꿈 | WeasyPrint가 오른쪽에 빈 공간이 있어도 flex 항목 폭을 내용보다 좁게 잡는다 | 머리글·배지에 `white-space: nowrap` + `flex-shrink: 0` |
| 표지가 넘쳐 꼬리말만 있는 6번째 페이지 발생 | 세로 flex + `.title-hero { flex: 1 }`로 만든 "남는 공간"을 변환기마다 다르게 계산 | 표지를 블록 레이아웃으로 교체해 높이를 내용만으로 결정 |
| 상태 배지 앞 점이 원이 아니라 세로 막대 | `::before`가 flex 항목이 되지 않아 `width/height` 무시 | `display: inline-block` + `vertical-align: middle` |

세 번째 항목은 `display: inline-block`만 주면 baseline 정렬 때문에 줄 높이가 늘어 **그 한 줄만으로 다시 5→6페이지가 됐다**(실측). `vertical-align: middle`로 증가를 없애고, 표지 여백을 줄여 여유를 33pt → 54pt로 늘렸다.

**3페이지 높이는 2026-08-10에 다시 쟀다.** 진단이 4섹션으로 나뉘면서 556~580px에서 **639~720px**로 늘었다(여유 311~392px, 넘침 0). 높이가 80px 폭으로 흔들리는 이유는 LLM이 쓰는 문장 길이가 이벤트마다 다르기 때문이다 — 연쇄 영향 항목 수를 `DIAGNOSIS_MAX_CHAINED_EFFECTS`(3)로 제한해 이 폭을 묶어 둔다. 요약 박스의 강조선 색은 상태를 따른다(`.diag-summary.status-fault`) — 팔레트가 단조 증가 램프이므로(§5-3 참조: `05_ui_screens.md`) FAULT 리포트에 DANGER 색을 쓰면 가장 심각한 상태가 약해 보인다.

**남은 여유는 콘텐츠에 돌려준다.** 3페이지로 압축하던 동안 줄였던 여백·글꼴을 되돌리고 더 키웠다 — 센서 카드는 4열 세로 배치에서 2×2 가로 배치로 복구(아이콘 26→38px, 값 19→24px), 측정 근거 칩·지표 특성·의심 고장 모드 항목의 글꼴과 패딩도 올렸다. 분석 요약 본문은 `line-height: 1.75`로 띄웠다. 그래도 최소 여유가 116px 남는다.

**섹션을 한 페이지에 몰아넣지 않는 이유.** `.page`에 `page-break-after: always`를 걸어도 **내용이 본문 높이를 넘으면 그대로 흘러넘쳐 페이지가 밀린다.** 3페이지로 압축했을 때 실측 여유가 7~28px까지 떨어졌는데, 이 폭은 모터 한 대만 바뀌어도 사라진다 — 137호기(소음)는 SOP 첫 문장이 두 줄이 되면서 같은 배치에서 49px가 넘쳤다. 높이 변동 요인은 SOP 문장 길이, 의심 고장 모드의 근거 문장 길이, 동반 이상 지표 유무다.

섹션마다 끊으면 **최소 여유가 116px**로 올라가 어느 모터든 안정적이고, 페이지를 따로 떼어 보여줘도 내용이 완결된다.

**섹션 번호를 독립적으로 부여한다.** 종전에는 근본 원인 분석이 `2-1. … (근본 원인 분석 계속)`이라 2번 페이지 없이는 읽히지 않았다. 페이지를 따로 배포·인쇄할 수 있어야 하므로 `2. AI 진단` / `3. 근본 원인 분석`으로 분리하고, 이후 번호를 밀었다(SOP 4번, 대응 이력 5번).

**모든 내용 페이지에 머리글을 반복한다.** `report_content_header.html` 파셜을 `{% include %}`로 넣어, 어느 장을 봐도 모터 ID·이름·상태를 알 수 있게 한다.

**이벤트 감지 시각 배너는 두지 않는다.** 표지의 "감지 시각"과 같은 값을 75px 들여 반복하던 블록이다. 섹션 5 타임라인 첫 항목에도 같은 시각이 나오므로 잃는 정보가 없다.

내용이 페이지 경계에서 잘리지 않도록 `@media print`에 `break-inside: avoid`(카드·센서·근거 칩·고장모드·SOP 항목·타임라인·표 행), `h2 { break-after: avoid }`(제목만 페이지 끝에 남는 고아 방지), 목록 `orphans/widows: 2`를 건다.
