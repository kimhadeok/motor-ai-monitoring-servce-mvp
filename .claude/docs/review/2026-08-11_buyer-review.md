## 1. 한 줄 결론

**안 산다.** 조건부도 아니다 — 지금 이건 **제품이 아니라 화면 시제품**이다. 우리 설비를 연결할 수단이 코드에 존재하지 않고(수집 API 0건), 알림이 나가지 않으며(발송 코드 0건), 새 이상을 감지하는 경로 자체가 없다. **유상 PoC 계약이라면 앉아서 이야기할 가치는 있다.**

## 2. 돈을 내게 만드는 것

**(1) AI가 헛소리를 하면 스스로 막는다 — 이게 제일 인상적이었다.**
`app/agents/diagnosis_agent.py`의 `_verify()`가 GPT 출력에 실제 측정값이 인용됐는지 정규식으로 뽑아 오차 0.05 이내로 대조하고, 하나도 안 맞으면 그 진단을 통째로 버리고 규칙 기반으로 갈아치운다. 그리고 리포트의 모델 라벨을 `"규칙 기반 진단 (LLM 미사용)"`으로 바꿔 **AI가 안 돌았다는 사실을 담당자에게 숨기지 않는다**(`06 §2.3`).

다른 벤더에서 "AI가 진단합니다"를 열 번 들었지만, "AI가 그럴듯한 말을 하면 우리가 걸러냅니다"를 설계로 보여준 건 처음이다. 게다가 문서에 **자기 코드가 거짓말한 걸 스스로 잡아낸 기록**이 있다 — 전류 이상 리포트에도 "온도와 진동이 함께 상승하는 패턴은 베어링 윤활 부족의 전형적 징후"가 나갔고 24건 중 맞은 게 1건이었다고 적혀 있다.

**(2) 리포트가 실제로 나온다 — 배포 환경에서 검증된 PDF.**
A4 5페이지, 섹션당 한 페이지, 한글 글리프 정상. 브라우저에서 잰 레이아웃이 실제 PDF와 달라 6페이지로 깨졌던 것을 배포 환경과 같은 Debian 컨테이너로 재검증한 절차까지 있다. **정비 팀에 종이로 돌릴 수 있는 물건**이다.

**(3) 경보 피로를 진지하게 다뤘다.**
전이 확정 5분 연속 유지 + 회복 시 5% 이력폭(`02 §2.3`). 실측으로 전이 25건 → 9건, 30분 내 왕복 0건. **현장 사람이 왜 알림을 꺼버리는지 아는 설계**다.

**(4) 대시보드 첫 화면이 "지금 뭘 해야 하나"에 답한다.**
타일 4칸(조치 필요 / 주의 관찰 / 최근 24시간 이벤트 / 마지막 수집), 그 아래 배너가 **설비 이름을 직접 부른다**. 특히 세 번째 배너 — "정비 완료 확인을 마쳤지만 여전히 고장 임계를 넘는 값이 들어옵니다." 확인 버튼을 눌렀는데 값은 안 내려간 상황을 따로 만들어 뒀다. **현장 겪어본 사람이 만든 화면이다.**

**(5) 리포트가 "우리가 통보했다"를 실제 기록으로 쓴다.**
`notification_logs`를 조회해 수신 담당자·채널·문구를 그대로 싣고, 기록이 없으면 "발송 없음 — 쿨다운"으로 사실대로 적는다(`06 §2.5`).

## 3. 이게 없으면 못 산다

**(1) 우리 설비를 연결할 방법이 존재하지 않는다 — 이 하나로 구매가 끝난다.**
`02 §2.1`은 "API를 통해 수신 → DB 저장"이라고 적혀 있지만 **소스에 그 API가 없다.** FastAPI·Flask·엔드포인트·MQTT·Modbus·OPC-UA 전부 **0건**. 데이터가 들어오는 유일한 경로는 시드가 난수로 그리는 시나리오다.
> 왜 결정적인가: "연동 기간 2주"가 아니라 **수집 계층 미개발**이다. 시연의 210대는 전부 가상이다.

**(2) 알림이 발송되지 않는다 — 로그만 쌓인다.**
KAKAO·알림톡·SMS·SMTP·HTTP 클라이언트 전부 0건. 존재하는 건 채널 이름 문자열 3개뿐이다.
> 왜 결정적인가: 예지보전의 값어치는 **새벽 3시에 담당자 휴대폰이 울리는 것**에서 나온다. 대시보드를 열어야만 안다면 감시 시스템이 아니라 조회 화면이다.

**(3) 실시간이 아니다 — 새 이상은 절대 감지되지 않는다.**
10초 자동 갱신은 진짜지만 갱신되는 건 **숫자뿐**이다. `remaining_work` #2: "틱은 상태를 바꾸지 않는다". 값은 마지막 행이 속한 상태 구간 안에서만 흔들리도록 묶여 있다.
> **화면의 FAULT 4대·DANGER 13대는 부팅 순간 시드가 만든 전이 80건이 전부고, 앱을 켜둔 동안 새로 생기는 이상은 0건이다.** 통신이 끊겨도 아무 일도 일어나지 않는다.

**(4) 임계값을 우리 설비에 맞게 바꿔도 판정이 안 바뀐다.**
관리자 페이지에서 저장한 값은 `motor_thresholds`에 들어가지만, 이 테이블을 읽는 곳은 **모터 상세의 임계값 표와 리포트의 참고표 두 군데뿐**이다. 상태 판정·카드 게이지·차트 임계선·진단 근거는 전부 `config.METRIC_THRESHOLDS` 전역 하드코딩을 쓴다.
더 나쁜 건 `admin.py`의 주석이 "순서가 뒤집히면 상태 판정이 성립하지 않아 화면이 조용히 잘못된 상태를 보여준다"고 적혀 있다는 점 — **판정에 쓰인다고 믿고 쓴 코드인데 실제로는 안 쓰인다.**
> 왜 결정적인가: 37kW 송풍기와 5.5kW 펌프의 정상 온도가 같을 리 없다. 설비별 임계 튜닝은 예지보전의 첫 단추다. 지금은 **리포트가 자기모순을 일으킨다.**

**(5) 데이터가 2시간 만에 통째로 지워진다.**
`bootstrap.py`가 최신 텔레메트리 2시간 초과 시 DB 파일을 `unlink()` 한다. 보관 범위도 48시간이다.
> 이 제품 자기 RAG 파일에 "베어링 결함은 **학습 기간 대비 추세 변화**로 더 일찍 드러난다"고 적혀 있는데, **48시간으로는 학습 기간이 성립하지 않는다.**

## 5. 속았다고 느낄 뻔한 것

1. **배포본의 "AI 진단"은 AI가 아니다.** Secrets에 `DIAGNOSIS_LLM_ENABLED="false"`. 벤더가 보여주는 배포 URL에서 리포트를 열면 규칙 기반 문장이다. 라벨은 정직하게 바뀌지만 **시연 자리에서 그 작은 글씨를 읽는 사람은 없다.**
2. **리포트 타임라인의 시각이 계산된 값이다.** `06 §2.5` — "발송 시각은 리포트 생성 시각(이벤트+12초)을 쓴다." 사고 조사에 쓸 문서에 계산해서 만든 시각이 찍히면 안 된다.
3. **"예지보전"이 아니라 "임계 초과 후 설명"이다.** 예측·RUL·이상탐지·FFT 전부 0건. "수일 내 조치"는 `fault_modes.json`의 정적 매핑 조회다.
4. **데모 데이터가 정답을 미리 알고 있다.** 시드가 "이 모터를 FAULT로 만들자"고 정해 놓고 목표치까지 선형으로 램프시킨다. 진단이 수치를 정확히 맞히는 건 당연하다. **시연에서 볼 수 없는 것: AI가 사람이 못 본 걸 잡아내는 장면.**
5. **로그인한 누구나 설비를 지울 수 있다.** role 없음. 모터 삭제는 텔레메트리·상태로그·알림 연쇄 삭제다. 로그인 화면이 시연 계정과 공통 비밀번호를 노출·자동입력한다.
6. **정비 이력이 남지 않는다.** "정비 완료 확인"은 상태 로그 한 줄이 전부 — 뭘 교체했는지 적을 칸이 없고 CSV 내보내기도 없다. **경영진에 낼 "절감액 X원"을 만들 데이터가 안 쌓인다.**

## 7. 개발팀에 묻고 싶은 것

1. **설비 200대에서 시스템까지 데이터가 오는 경로를 그려 달라.** 센서 모델·게이트웨이·프로토콜·수집 API. **어디까지가 귀사 제품이고 어디부터가 우리 몫인가?** 개발에 몇 개월인가?
2. **"틱은 상태를 바꾸지 않는다"를 걷어내는 데 무엇이 필요한가?** 아키텍처가 안 정해진 것인가, 호스팅만 바꾸면 되는가? 답에 따라 남은 개발량이 몇 배로 갈린다.
3. **관리자에서 임계값을 바꾸면 상태 판정이 실제로 바뀌는가? 알고 있었는가?** 모르고 있었다면 "저장은 되는데 안 쓰이는" 항목 전수 점검 결과를 달라.
4. **오탐과 미탐을 어떻게 측정하고 보증에 쓸 숫자가 있는가?** 실제 설비 데이터로 검증한 결과가 하나라도 있는가? PoC 성패 판정 기준은?
5. **데이터 보관 기간과 반출 방법은?** 정비 이력 입력·CSV 내보내기 계획은? **계약 종료 시 우리 데이터를 어떤 형식으로 넘겨받는가?**

## 개발팀 확인 결과 (2026-08-11, coreagent)

**3-(4) 임계값 지적은 사실로 확인됐다.** 사본 DB에서 재현:

- `motor_thresholds`를 읽는 곳은 표시용 2곳뿐(`motor_detail.py`, `reports/service.py`의 참고표). 판정·게이지·차트 임계선·진단 근거·틱 값 범위는 전부 `config.METRIC_THRESHOLDS`.
- MTR-233의 온도 임계를 경고 50/위험 65/고장 80으로 바꾸자 **같은 리포트 한 장 안에서** 센서 카드 "정상 기준 ≤ 60.0 °C"(config)와 임계값 표 "정상 구간 < 50"(DB)이 **동시에** 찍혔다.
- 게이지 눈금도 `warning_at = 0.667`(= 60/90)로 config 기준을 유지했다.

**5-(1) 배포본 AI 진단 지적도 사실이었고, 방침을 바꿨다 (2026-08-11).** 배포 로그 실측 `diagnosis_llm=off`로 확인됨. 종전 우려는 "공개 URL이라 GPT-4o 호출을 통제할 수 없다"였는데, 호출 구조를 재확인하니 **노출이 유계**였다 — 호출은 [보고서] 클릭당 최초 1회뿐이고(부팅 경로에 LLM 없음), `report_html` 캐시로 재열람은 호출이 없으며, 부팅 1회당 상한이 24호출(DANGER 19 + FAULT 5)이다. 배포본 Secrets를 `DIAGNOSIS_LLM_ENABLED="true"`로 바꾼다(`README` 배포 절, `02 §6.5`, `remaining_work #5`). 지적대로 **시연 자리에서 라벨 작은 글씨를 읽는 사람은 없다**는 쪽이 더 큰 손실이라 판단했다.

나머지 지적(수집 API·알림 발송·실시간 감지·데이터 보관)은 `README`와 `remaining_work`에 **MVP 범위 밖으로 이미 명시**된 것과 일치한다. 검토자가 "MVP니까 괜찮다로 넘어가지 않겠다"고 한 판단은 구매자 관점에서 타당하다.
